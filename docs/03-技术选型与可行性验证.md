# 03 · 技术选型与可行性验证

## 3.1 三条候选技术路线

| | **路线 A：纯浏览器静态站** | **路线 B：自托管服务端** | **路线 C：混合（A 为主 + 可选 B）** |
|---|---|---|---|
| 形态 | 静态 HTML/JS，部署到免费 CDN | Python 服务 + 前端 | A 为默认，允许用户填入自己的加速后端 |
| 识别 | 浏览器原生 / WASM / WebGPU | faster-whisper | 两者都有 |
| 翻译 | 浏览器内置 API / ONNX | M2M-100 / NLLB | 两者都有 |
| 摘要 | 本地小 LLM / 抽取式 | 任意 LLM | 两者都有 |
| 服务器成本 | **¥0** | 云 GPU 每月数十到数百元，或自己的电脑常开 | ¥0 |
| 朋友能否用 | ✅ 发链接即可 | ❌ 得访问你的服务，你得一直开机 | ✅ 默认可用 |
| 质量上限 | 中（小模型） | 高（大模型） | 高（愿折腾的人自取） |
| 部署难度 | 极低 | 高 | 低 |

### 结论：采用 **路线 C**，但一期只实现 A 的部分

理由：

1. **只有 A 能无条件满足「零费用 + 发链接给朋友用」这两条硬需求**（§1.3）。B 必须有一台机器 7×24 开着，对个人项目就是持续成本。
2. hayamimi 的实测说明了一个反直觉的事实：**量化小模型在专用任务上可以打败通用大模型**（日语 CER 3.8% vs whisper-large-v3-turbo 13.8%）。浏览器端小模型不等于体验差。
3. C 比 A 只多一个**可选的引擎挂载点**，几乎不增加实现成本，却给未来的质量升级留了门。

## 3.2 核心设计：四层渐进增强引擎

「渐进增强」是本项目最重要的架构原则。原因是实测发现设备能力差异极大：

### 已验证的硬性限制（来自 Chrome 官方文档）

| 项目 | 事实 |
|---|---|
| 浏览器支持 | Chrome **138+**、Edge **148+**，**仅桌面端** |
| **不支持** | **Android、iOS、Firefox、Safari 全部不支持** |
| 操作系统 | Windows 10/11、macOS 13+、Linux、ChromeOS |
| 磁盘 | 至少 **22GB** 可用空间 |
| 内存 | **16GB+** |
| CPU | 4 核以上 |
| GPU | **4GB+ VRAM**（Prompt API 处理音频时强制要求） |
| 网络 | 仅首次下载语言包需要；**模型下载后翻译全程不向 Google 发送数据** |
| Web Worker | **不支持**（Permission Policy 限制） |
| 跨域 iframe | 需显式 `allow="translator"` |
| 已废弃 | `window.ai.translator` 命名空间**不可使用** |
| 支持语言 | 含 `en`、`zh`、`zh-Hant` 等约 38 种 |

**这张表直接判了「只靠内置 API」这条路死刑**：手机不支持 + 22GB 磁盘 + 16GB 内存，意味着大多数设备根本拿不到这个能力。

### 于是设计成四层，逐层尝试、逐层降级

```
                    ┌─────────────────────────────────────────┐
   引擎解析顺序 →    │  L0 浏览器原生 (最快最省事)              │
   (照抄 otoji      │      ↓ 不可用                            │
    的优先级思路)     │  L1 本地小模型 WebGPU (快，需好显卡)      │
                    │      ↓ 不可用                            │
                    │  L2 本地小模型 WASM (慢但全能跑)          │
                    │      ↓ 不可用                            │
                    │  L3 抽取式/规则兜底 (永远可用)            │
                    └─────────────────────────────────────────┘
```

| 环节 | L0 原生 | L1 WebGPU | L2 WASM | L3 兜底 |
|---|---|---|---|---|
| **识别 ASR** | Web Speech API（Chrome/Edge/Safari 均可用，流式，零下载） | Whisper-base/small via transformers.js WebGPU | Whisper-tiny via WASM | 提示用户改用「上传音频文件」模式 |
| **翻译 MT** | Chrome/Edge `Translator` API（桌面限定） | opus-mt-en-zh / NLLB-600M via WebGPU | 同模型 via WASM | 词典 + 模板直译（质量差但可用） |
| **摘要 SUM** | — | WebLLM Qwen2.5-1.5B-Instruct q4 | Qwen2.5-0.5B via WASM | **TextRank 抽取式**（纯 JS，毫秒级，永远成功） |

**关键设计**：L3 摘要兜底是纯 JS 的抽取式算法，不需要任何模型、不占内存、不会失败。这保证「**任何设备打开都至少能拿到一份要点列表**」这条底线。

### 关于 Web Speech API 的必须标注事项

Web Speech API 是**免费**的，也是 Chrome / Edge / Safari 全平台可用、真流式的，作为 L0 兜底非常合适。但需要向用户明确披露：

- 在 Chrome 上，识别过程**很可能把音频发送到 Google 的服务器**处理（这是公开讨论已久的行为，与完全本地的 ONNX 推理不同）。
- 因此产品上应提供明确的开关与说明：
  - 「⚡ 快速模式」= Web Speech API：零下载、延迟最低，但音频可能经过第三方服务器。
  - 「🔒 私密模式」= 本地 ONNX 模型：需下载模型，音频绝不离开设备。
- **待 M0 实测确认**：Safari / Edge 上的具体行为差异（列入 §3.6 验证清单）。

## 3.3 逐环节选型明细

### ① 音频采集与断句（VAD）

| 项 | 选择 | 理由 |
|---|---|---|
| 采集 | `getUserMedia` + `AudioWorklet` | AudioWorklet 在独立线程做重采样，不卡 UI（`ScriptProcessorNode` 已废弃） |
| 格式 | **16kHz 单声道 Float32** | 与 WhisperLive 的约定、Whisper 输入、sherpa-onnx 输入全部一致 |
| VAD | **Silero VAD ONNX**（`@ricky0123/vad-web`）或能量+过零率自研 | 抄 hayamimi：**0.35s 静音断句 + 0.8s 预滚**（预滚防止吃掉句首音） |
| 断句参数 | 静音 0.35s 断句 / 最长连续语音 12s 强制切分 | 直接沿用 hayamimi 的默认值作为起点 |

### ② 语音识别（ASR）

| 候选 | 体积 | 流式 | 移动端 | 英文质量 | 结论 |
|---|---|---|---|---|---|
| Web Speech API | 0 | ✅ 真流式 | ✅ | 很好 | **L0 首选**（但国内音频要发往 Google，实测这条路不通，见 R15） |
| Whisper-tiny.en (transformers.js) | **实测 42.4MB**（q8） | ⚠️ 需分块模拟 | ✅ | 够用 | **L1 默认，已落地并自托管** |
| Whisper-base (transformers.js) | ~150MB | ⚠️ 需分块模拟 | ⚠️ WASM 吃力 | 好 | ❌ **已移除**：自托管下多一份体积 |
| Whisper-small | ~500MB | ⚠️ | ❌ | 很好 | ❌ **已移除**（同上） |
| Moonshine / Parakeet TDT（ONNX） | ~200–600MB | ⚠️ | ⚠️ | 很好 | 备选，需实测 |
| sherpa-onnx 流式 Zipformer | ~100MB | ✅ 真流式 | ✅ | 好 | **重点实测候选**：真流式 + 小体积 |

**决策**：L1 用 **Whisper-tiny.en q8（42.4 MB，MIT，已随站点自托管）**；
L0 的 Web Speech 在桌面仍是首选，但在国内这条线上**它其实也不通**（音频要发往 Google 服务器），
所以对它不能抱期望。L1/L2 的下一步是实测 **sherpa-onnx 流式模型**，
因为它同时满足「真流式 + 小体积 + 移动端可行」，恰好补上 Web Speech 的隐私缺口。
模型候选从 4 个砍到 1 个的原因见 [`07`](07-风险与对策.md) R15。

### ③ 翻译（EN → ZH）

| 候选 | 体积 | 需要什么 | 结论 |
|---|---|---|---|
| Chrome/Edge `Translator` API | 0（语言包由浏览器管） | 桌面 Chrome 138+ / Edge 148+ | **桌面 L0 首选**，质量与速度最好且免费 |
| opus-mt-en-zh (transformers.js) | **实测 117.2MB**（q8） | 任意环境 | **移动端主力**，也是唯一的本地翻译候选 |
| NLLB-200-distilled-600M | ~600MB | 好显卡 | ❌ **已移除**：自托管下每多一个候选就多一份必须随站点发布的体积 |
| WebLLM + Qwen 做翻译 | ~1GB | WebGPU | ❌ **已移除**（同上），列为 M6 可选 |

**决策**：
- 桌面 → `Translator` API（注意：`sourceLanguage`/`targetLanguage` 必须**原样同时**传给 `Translator.availability()` 和 `Translator.create()`；下载语言包**必须由用户手势触发**，否则抛 `NotAllowedError`）。
- 移动端 → opus-mt-en-zh WASM。
- **必须实现 `Translator.availability()` 四态处理**：`available` / `downloadable` / `downloading` / `unavailable`，并在界面上给出对应反馈（尤其是下载进度条，用 `downloadprogress` 事件）。

### ④ 摘要（本项目差异化核心）

**两段式设计**：

```
实时阶段：维护滚动双语稿 + 一个「窗口摘要」缓冲区
          （每 N 句或每 60s，对增量做一次轻量摘要，缓解长文超上下文）
                          ↓
结束阶段：对「精修后的完整转写」做一次全局结构化摘要
          输出：主题 / 要点 bullets / 关键数字 / 结论 / 待办
```

| 候选 | 体积 | 质量 | 移动端 | 结论 |
|---|---|---|---|---|
| **TextRank 抽取式（纯 JS）** | 0 | 只是挑句子，不生成 | ✅ 完美 | **L3 永远的兜底** |
| **Qwen2.5-0.5B-Instruct ONNX** | ~400MB | 可接受 | ⚠️ 勉强 | 移动端 L2 |
| **WebLLM Qwen2.5-1.5B-Instruct q4f16** | ~1GB | 好 | ❌ | 桌面 L1 主力 |
| 用户自带 API Key（BYOK） | 0 | 最好 | ✅ | 可选增强，**默认关闭**，绝不作为必需路径 |

**决策**：
- 默认走本地模型；`unavailable` 时自动降级到 TextRank。
- **BYOK 是可选增强**：用户自己填 key 就用更好的模型，不填也完全可用。这样既守住「零费用」又能让挑剔的用户自己提升质量。
- **关键工程细节（来自 hayamimi 的教训）**：小模型翻译**数字不可靠**，所以摘要模块必须把「原始英文里的数字/日期/专有名词」单独抽取出来，作为不受翻译影响的独立字段展示。

### ⑤ 存储与状态

| 项 | 选择 | 理由 |
|---|---|---|
| 会话记录 | IndexedDB（`idb` 库） | 大对象、离线、不上云 |
| 偏好设置 | localStorage | 小、简单 |
| 模型缓存 | **Cache Storage API** | 配合 transformers.js 的缓存机制，模型下载一次永久复用 |
| 状态管理 | Zustand 或自研轻量 store | 场景简单，不需要 Redux（ScribeAR 用 Redux 是因为它要管多 app） |

### ⑥ 前端技术栈

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **React 19 + TypeScript + Vite** | 生态最全，transformers.js / WebLLM 的示例最多 |
| 样式 | **Tailwind CSS** | 快速做出像样的界面 |
| 组件 | shadcn/ui（按需引入） | 不引入整套组件库 |
| 音频 | `@ricky0123/vad-web` + Web Audio API | VAD 现成方案 |
| 推理 | `@huggingface/transformers`（transformers.js **v4**）+ `@mlc-ai/web-llm`（可选，M6） | 浏览器端 ONNX/WebGPU 事实标准 |
| 打包 | Vite + `vite-plugin-pwa` | 静态产物 + PWA 离线能力 |
| 测试 | Vitest（单测）+ Playwright（E2E，含移动端模拟） | 引擎降级逻辑必须测 |

## 3.5 性能预算

| 指标 | 目标 | 依据 |
|---|---|---|
| 首字上屏 | ≤ 1.5s | hayamimi partial 每 ~0.5s 刷新 |
| 整句译文 | ≤ 2.5s | 内置翻译 API 为毫秒~百毫秒级；本地小模型需 ~1s |
| 首次加载（不含模型） | ≤ 2s | 静态站，gzip 后 < 500KB |
| 模型下载 | 分档提示 | 轻量 ~150MB / 标准 ~400MB / 高质量 ~1GB |
| 常驻内存 | ≤ 1.5GB | 抄 hayamimi 的 LRU 上限思路 |
| 10 分钟讲话的摘要耗时 | ≤ 15s（本地 LLM）／ ≤ 0.5s（TextRank） | — |

## 3.6 待实测验证清单（M0 阶段的攻关目标）

这些是**文档无法定论、必须写代码实测**的问题，也是本项目最大的不确定性来源：

| 编号 | 待验证问题 | 为什么关键 | 验证方法 |
|---|---|---|---|
| V1 | 手机上跑 opus-mt-en-zh WASM，一句翻译要多久？ | 若 > 3s，移动端体验就不成立 | 写最小 demo，在真机 Chrome Android + iOS Safari 上计时 |
| V2 | 手机上 Whisper-tiny / sherpa-onnx 流式模型的实时率（RTF）是多少？ | 决定移动端能否用本地 ASR | 同上，测 RTF 与内存峰值 |
| V3 | iOS Safari 的 Web Speech API 是否真流式、是否本地处理？ | 决定 iOS 用户的体验与隐私叙事 | 真机实测 + 断网测试 |
| V4 | 桌面 Chrome `Translator` API 在 16GB 内存以下机器上能否拿到？ | 影响降级比例 | 在多台真机上跑 `Translator.availability()` |
| V5 | WebLLM Qwen2.5-1.5B 在集显笔记本上的摘要速度 | 决定桌面摘要默认走哪条路 | 真机测 10 分钟转写的摘要耗时 |
| V6 | 中文译文分句与英文原文的对齐效果 | 双语对照的观感 | 人工评估若干段真实演讲 |
| V7 | Web Speech API 的断句粒度能否满足「实时」感 | 它是 L0 识别主力 | 实测连续讲话的中间结果刷新频率 |
| V8 | 模型缓存能否在浏览器存储配额内稳定存活 | 影响「第二次打开是否还要下载」 | 反复开关页面测 Cache Storage 命中 |

**M0 的交付物就是这 8 个问题的实测报告**，它决定 §3.2 的四层引擎里哪些层真正可用。
