# 02 · 同类项目调研与优劣分析

## 2.1 调研方法

- 检索词覆盖中英双语：`real-time speech translation web app`、`实时的语音翻译 开源`、`browser-side whisper realtime`、`meeting transcription summary self-hosted`。
- 筛选标准：① 实时语音→文本；② 至少含翻译或字幕输出；③ 开源可读源码；④ Web/浏览器相关。
- 共找到 4 个高相关项目做深度分析，另有 2 个作补充参考。

## 2.2 主参考项目：otoji（音字）— `snomiao/otoji`

> **为什么它是最佳学习对象**：它是本次调研中**唯一把「浏览器本地推理 + 免密钥 + 分享链接」三件事同时做成的完整产品**，与我们的零成本 + 可分享约束高度重合。

**网址**：https://github.com/snomiao/otoji ｜ 线上：https://otoji.org
**许可**：MIT

### 它的定位

> realtime speech ⇄ text — 把 `mic → STT → translate → speech` 连成一张「语音图」，跑在你自己的设备上。无账号、无 API Key，默认什么都不离开浏览器：ASR、翻译、TTS 全部在设备本地运行（transformers.js / onnxruntime-web / WebGPU / WASM）。

### 它的架构（原文结构图）

```
   phone                         laptop                        any device
 ┌─────────┐   opus/segment    ┌──────────────┐   transcript  ┌──────────┐
 │ Mic+VAD ├══════════════════>│ SenseVoice    ├═════════════>│ Translate │──► 🔊 / 📝 / .srt
 └─────────┘   WebRTC (P2P)    │ STT           │   WebRTC      └──────────┘
                               └──────────────┘
```

关键设计点：

1. **节点图（voice graph）模型**：每个节点有带类型的端口（`segment` 音频 / `transcript` 文本），只有类型匹配才能连线。同设备连线在进程内执行，跨设备连线自动变成 WebRTC 数据通道。这是一个非常优雅的抽象——把「音频管线」和「分布式」统一成一件事。
2. **房间 + 可分享 URL**：`otoji.org/keen-gibbon-4a0d` 这种 Google-Meet 式链接，扫码/发链接即可加入。
3. **唯一服务器只做信令**：Cloudflare Durable Object 负责在线状态、SDP/ICE 中继、图的权威状态同步，**从不接触音频**。这是「零成本 + 隐私」能同时成立的核心技巧。
4. **模型 P2P 共享**：模型每台设备下载一次，房间内可 P2P 传给其他设备，只有一台设备付出下载成本。
5. **解析顺序**（非常重要的一行设计）：`本地进程内 > 本地服务器 > 云 API > 禁用`。云服务是**可选兜底**而非默认路径。

### 它的节点目录（可直接对照我们的功能需求）

| 类别 | 节点 |
|---|---|
| 输入 | 麦克风 + VAD · 麦克风（原始，无 VAD）· 音频文件输入（拖放或 URL）· 文本文件输入 |
| 语音 → 文本 | SenseVoice STT（ONNX，多语言 + 情感/事件标签）· Web Speech（浏览器流式）· Vosk（Kaldi/WASM 流式） |
| 文本 → 文本 | 翻译 —— 浏览器内 LLM（WebLLM）或浏览器 Translator API |
| 文本 → 语音 | 浏览器 SpeechSynthesis · 神经 TTS（本地 ONNX MMS-TTS） |
| 输出 | 转写记录 + 录音 · 音频文件输出 · SRT 字幕输出 · 扬声器播放 |
| 自定义 | 任意 transformers.js 模型（按 repo/URL） |
| 管道 | CLI stdio 桥接 |

### 优点

| 优点 | 具体表现 | 我们能学到什么 |
|---|---|---|
| **真·零成本落地** | 全部推理在端上，无密钥、无按量计费 | 验证了「零成本」不是空想，是有成熟实现的 |
| **隐私叙事强** | 默认不出设备，云端是 opt-in | 我们的隐私承诺可以照抄这个「默认本地」的立场 |
| **引擎可替换** | 同一能力提供多个实现（STT 有 3 个节点，翻译有 2 个） | 印证了我们「每环节可独立替换引擎」的设计 |
| **分享体验好** | 可分享房间 URL、手机采集 + 电脑算力的分工 | 「传链接给朋友」这个需求有现成范式 |
| **降级链清晰** | `本地进程内 > 本地服务器 > 云 API > 禁用` | 直接采纳为我们的引擎解析顺序（去掉云 API） |
| **工程完整** | 有浏览器扩展 + 用户脚本、Rust 核心 + napi 绑定、CLI 桥 | 说明这个技术栈撑得起完整产品 |

### 缺点 / 我们的不同选择

| 缺点 | 说明 | 我们的对策 |
|---|---|---|
| **没有「结束总结」** | 它输出的是转写文本和 SRT，不做要点提炼 | **这就是我们的差异化功能 F3/F4** |
| **架构过重** | 「语音图编辑器 + WebRTC 网状网 + 跨设备」对普通朋友来说是认知负担 | 一期放弃房间与图编辑，做**单页即用**的极简形态 |
| **仍需一个服务器** | Cloudflare Durable Object 是免费额度，但仍是服务端依赖 | 一期**彻底不要服务端**，连信令都不需要 |
| **STT 选型偏中文/亚洲语种** | SenseVoice 强项在 zh/ja/ko/yue，英译中不是它的最优场景 | 我们源语言固定是英文，应选**英文更强的引擎** |
| **上手门槛高** | 图编辑器、节点连线的学习成本 | 我们要的是「按一个按钮就开始说话」 |

### 借鉴清单（结论）

- ✅ **采纳**：引擎解析顺序 `本地 > 可选增强 > 禁用`；每环节多实现可替换；默认本地/隐私优先；SRT 与转写导出。
- ⚠️ **晚点再说**：房间、WebRTC 跨设备、模型 P2P 共享（远期 M7+）。
- ❌ **不采纳**：图编辑器形态（一期直接做单页固定管线）。

## 2.3 工程参考：hayamimi（早耳）— `oboroge0/hayamimi`

> **为什么它重要**：如果 otoji 教我们「怎么免费地做」，hayamimi 教我们「怎么把实时同传这条流水线**做对**」。它的文档是我见过同类项目里最诚实的。

**网址**：https://github.com/oboroge0/hayamimi
**许可**：源码 MIT；**模型权重不含在仓库内**，由 `scripts/download_models.py` 在安装时各自下载，各自带自己的许可。

### 它的流水线（原文架构图，抽取核心）

```
mic/wav → [Silero VAD] 0.35s 断句 + 0.8s 预滚
        → [whisper-tiny spoken-LID] 语言识别（前 4s 内完成）
        → 路由到专业模型：ja=ReazonSpeech / zh=Paraformer-zh / ko+yue=SenseVoice
                        / en+24 种欧洲语言=Parakeet TDT v3 / 其他~1600 种=Omnilingual ASR
        → partial（每 ~0.5s 出草稿）‖ final（说完 ~100ms 出定稿）
        → [标点还原] [说话人标注 CAM++] [翻译 FuguMT / M2M-100]
        → 静音 2s 后：对最近几句做二次批量重解码（two-pass refine）
        → dashboard / OBS 叠加层 / 转写文件
```

### 实测数据（它的 scorecard）

| 语言 | 路线 | 平均错误率 | 平均 RTF |
|---|---|---|---|
| ja | ReazonSpeech | 3.8% CER | 0.090 |
| en | Parakeet v3 | 2.3% WER | 0.102 |
| zh | Paraformer-zh | 6.6% CER | 0.084 |
| ko | SenseVoice | 8.1% CER | 0.060 |
| yue | SenseVoice | 6.1% CER | 0.043 |

- **日语 CER 3.8%**，同一批真实广播音频上 `whisper-large-v3-turbo` 是 **13.8%**。
- **~100ms 平均定稿延迟**（日语，含标点）；5 语言全功能压测平均 236ms / 最大 552ms。
- **`--max-resident 3` 时内存 <2GB**（`--max-resident 2` 时 1.35GB）。
- RTF 全部 <0.2 ⇒ 每条路线在 6 核 CPU 上跑 9–16 倍实时。

### 优点

| 优点 | 具体表现 | 我们能学到什么 |
|---|---|---|
| **流水线工程极扎实** | VAD 断句 → LID → 专业模型路由 → 标点还原 → 二次精修 | 我们的管线阶段划分可以直接对齐 |
| **partial / final 双轨** | 边说话边出草稿（~0.5s 刷一次），停下 ~100ms 出定稿 | **同传体验的关键**：不能让用户干等整句 |
| **two-pass refine** | 静音 2s 后批量重解码，日语 CER 15.5% → 12.0% | 我们的「结束后总结」正好可以搭在这个精修结果上 |
| **量化 + ONNX + CPU-only** | 全部走 sherpa-onnx INT8，无 PyTorch 无 CUDA | 证明浏览器端量化小模型路线是可行的 |
| **LRU 淘汰控制内存** | `--max-resident` 控制常驻模型数 | 浏览器内存更紧张，这个机制必须抄 |
| **文档诚实** | 有专门的 "Limitations (honest list)" 章节 | 我们的 07 风险文档按这个标准写 |

### 缺点 / 硬伤

| 缺点 | 原文依据 | 对我们的启示 |
|---|---|---|
| **翻译方向只有「从日语出发」** | `--translate en,zh,ko,es` 是「translate Japanese lines live」 | 我们反过来，源语言是英语，翻译模型要重选 |
| **不是网站，是 Python 自托管** | 需要 Python 3.10+、ffmpeg、~3.1GB 模型 | 朋友不可能装这些 → 我们必须做成静态站 |
| **句内语码切换不支持** | "Code-switching mid-sentence is not supported"，混说会被吞或打乱 | 我们的界面要提示「一句只用一种语言」 |
| **重叠说话人分不开** | "Two overlapping speakers are not separated" | 说话人分离功能（F11）确实该后置 |
| **翻译质量有天花板** | FuguMT / M2M-100 是小模型，"repetition loops are suppressed but not eliminated"，且 "numeric values are not reliably preserved" | **重要**：数字不可靠 → 我们的总结功能必须把「原始英文数字」单独保留对照 |
| **多句连说会丢首句** | "Multi-sentence speech can still lose its leading sentence(s)" | 我们要有「转写长度 vs 语音时长」的异常检测 |
| **首句必须双 LID 确认** | 会话第一句总要用 SenseVoice 复核语言 | 我们源语言固定英文，可以直接跳过 LID，省掉这一整块复杂度 |

### 借鉴清单（结论）

- ✅ **采纳**：VAD 断句 + 预滚；partial/final 双轨；定稿后二次精修再喂给摘要；LRU 控制模型常驻；数字单独保留；诚实限制文档。
- 🔄 **改写**：源语言固定英文 ⇒ **砍掉整个语言识别与路由模块**，换成「英文专用最优模型」。
- ❌ **不做**：说话人分离、标点还原的日语专用模型。

## 2.4 部署参考：WhisperLive — `collabora/WhisperLive`

**网址**：https://github.com/collabora/WhisperLive ｜ 许可：MIT（以仓库 LICENSE 为准）

### 它是什么

> "A nearly-live implementation of OpenAI's Whisper." —— 一个实时转写服务端，支持麦克风与预录音频文件。

### 关键能力（对我们有参考价值的部分）

- **三种后端**：`faster_whisper`（CTranslate2）、`tensorrt`（NVIDIA TensorRT-LLM）、`openvino`（Intel CPU/iGPU/dGPU）。
- **服务端 WebSocket，默认端口 9090**，`--max_clients 4`、`--max_connection_time 600`。
- **两种翻译语义要分清**（这是个容易踩的坑）：
  - `translate=True`：Whisper 原生的**「任意语言 → 英语」**任务；
  - `enable_translation=True, target_language="hi"`：服务端另起翻译线程做**「任意 → 任意」**。
- **流式客户端** `StreamingTranscriptionClient`：自己推 PCM 字节流，回调 `on_partial_transcript` / `on_committed_transcript` / `on_translation`。**音频必须是 16kHz 单声道 PCM**，接受 `int16` 或 `float32`。
- **浏览器扩展**：官方提供 Chrome 与 Firefox 扩展，直接从浏览器抓音频。
- **词级时间戳**（`word_timestamps=True`，含每词 probability）、**热词偏置**（`hotwords`）、**说话人分离**（pyannote.audio 在线余弦聚类）、**批推理**（`--batch_inference --batch_max_size 8`）、**原始 PCM 输入**。
- **Docker 一键**：`ghcr.io/collabora/whisperlive-cpu:latest` 等。
- 上层还有生产级衍生项目 **Aavaaz**（说话人分离、情感分析、PII 脱敏、webhook、OpenAI 兼容 REST）。

### 优点

| 优点 | 说明 |
|---|---|
| 生态最成熟 | Docker 镜像齐全，CPU/GPU/Intel/AMD 全支持 |
| 协议清晰 | WebSocket + JSON 消息，前端接入成本低 |
| 回调接口设计好 | partial / committed / translation 三路回调，正好对应我们的 UI 三态 |
| 音频格式约定明确 | 16kHz 单声道 PCM —— 我们前端采集也应按这个标准 |

### 缺点

| 缺点 | 说明 |
|---|---|
| **必须有服务器** | 这是它和我们零成本约束的**根本冲突**：要一直跑一台有算力的机器 |
| 架构重 | `--max_clients 4`、模型加载、连接时长限制——都是运维负担 |
| 无总结能力 | 只有转写与翻译 |
| Whisper 非流式 | 「nearly-live」而非真流式，靠分块 + VAD 模拟 |

### 借鉴清单（结论）

- ✅ **采纳**：三路回调的 UI 状态模型（草稿 / 定稿 / 译文）；16kHz 单声道 PCM 作为内部音频标准。
- ✅ **采纳（作为远期选项）**：把「自托管 WhisperLive」做成 M7 的**可选加速后端**，让愿意自己跑服务的用户接上去。
- ❌ **不做**：把服务器作为一期的必需组件。

## 2.5 架构参考：ScribeAR — `scribear/scribear`

**网址**：https://github.com/scribear/scribear ｜ 背景：伊利诺伊大学的校园实时字幕系统

### 它是什么

> Self-hosted, real-time transcription. 一个完整 monorepo：语音转文字服务 + 代理/会话后端 + Postgres schema + 客户端/kiosk/独立 webapp。

### 仓库结构（对我们非常有借鉴意义）

```
apps/
  client-webapp/       # 观众端 —— 用 join code 加入会话，接收转写
  kiosk-webapp/        # 采集端 —— 发送房间音频的设备，显示加入二维码
  standalone-webapp/   # 二合一 viewer+source，不拆 kiosk/client
  node-server/         # 代理 kiosk/client 的 websocket 到转写服务
  session-manager/     # 设备、房间、会话、鉴权 —— 签发 session token
  admin-webapp/        # IT 管理台
  admin-server/        # 管理 BFF
infra/                 # Postgres schema + nginx
libs/                  # 类型化客户端 / 共享 schema / Redux slices / 共享 UI
transcription_service/ # Python：faster-whisper，CPU/CUDA
deployment/            # Docker Compose 全套
```

### 优点

| 优点 | 说明 |
|---|---|
| **「采集端 / 观看端」分离** | kiosk 采集 + client 观看 + 独立版三合一，这个三形态切分很聪明 |
| **join code + 二维码** | 房间加入方式极简，与我们「方便传给朋友」的需求同构 |
| **协议与 schema 共享** | `libs/schemas` 统一请求/响应定义，前后端不脱节 |
| **工程规范文档化** | 有 CONTRIBUTING、RELEASING、wiki 全套 |

### 缺点

| 缺点 | 说明 |
|---|---|
| **极重** | 6 个 app + Postgres + nginx + Docker Compose，个人项目完全不成比例 |
| 需要服务器与鉴权 | 又一次与零成本冲突 |
| 无翻译、无总结 | 纯转写字幕 |

### 借鉴清单（结论）

- ✅ **采纳**：`libs/schemas` 这一层——**前后端共享的消息 schema 先定义好**（我们一期虽无后端，但 Engine 之间的消息契约照此办理）。
- ✅ **采纳**：采集端 / 观看端分离的**思想**（不做成两个 app，但内部状态机分成 Capture 与 Render 两块）。
- ❌ **不做**：多 app monorepo、Postgres、鉴权体系。

## 2.8 全行业共同空白 → 我们的机会

把 6 个项目摊开看，功能矩阵的右半边是**整齐的一片空白**：

| 能力 | 覆盖情况 |
|---|---|
| 实时语音识别 | 6/6 都有，非常成熟 |
| 实时翻译 | 4/6 有 |
| 双语字幕显示 | 5/6 有 |
| 导出 SRT / 文本 | 3/6 有 |
| 说话人区分 | 2/6 有 |
| **结束后自动总结要点** | **0/6** |
| **零安装 + 零成本 + 手机可用 三者同时成立** | **0/6** |

于是本项目的两个立足点非常清楚：

1. **「同传即纪要」**：别人做完转写就结束了，我们把转写结果继续加工成中文结构化纪要。而且 hayamimi 的 two-pass refine 恰好给了我们一个**质量更好的输入**（静音 2s 后重解码的定稿），天然适合作为总结的素材。
2. **「手机也能开」的零成本形态**：otoji 最接近，但它仍需要一个 Cloudflare Durable Object 做信令。我们二期之前**彻底不要服务端**，把「发链接就能用」这件事做到极致。

## 2.9 总体借鉴结论

### 直接采纳（进入架构设计）

| 来源 | 借鉴点 |
|---|---|
| otoji | 引擎解析顺序 `本地 > 增强 > 禁用`；每环节多实现；默认本地 |
| otoji | 可分享 URL / 二维码作为分发形态 |
| hayamimi | VAD 断句 + 0.8s 预滚；partial/final 双轨；定稿后精修再总结 |
| hayamimi | LRU 常驻模型上限；「转写明显短于语音时长」的丢句检测 |
| hayamimi | 数字/专有名词单独保留对照（因为小模型翻译数字不可靠） |
| WhisperLive | 三路回调的 UI 状态模型；16kHz 单声道 PCM 内部标准 |
| ScribeAR | 先定义共享消息 schema；Capture / Render 状态分离 |

### 明确丢弃

| 丢弃项 | 理由 |
|---|---|
| 图编辑器形态 | 与「朋友打开即用」冲突 |
| WebRTC 房间 / 多人协作 | 一期引入信令服务器 = 破坏零成本 |
| 服务端 Python 推理（作为必需件） | 朋友无法部署；降级为 M7 可选加速后端 |
| 语言识别与多语言路由 | 我们源语言固定英文，整块复杂度可砍 |
| 说话人分离 | 难度高、非核心需求 |
| 浏览器扩展分发 | 需要用户安装，不如发链接 |

### 仍未解决、需要我们自己攻关的

| 问题 | 说明 |
|---|---|
| **浏览器端「英译中 + 摘要」的移动端可行方案** | 没有任何一个参考项目解决过这个（otoji 的手机端只做采集，不做推理）——**这是本项目最大的技术风险**，必须在 M0 阶段实测（见 [07 风险文档](07-风险与对策.md) R1/R2） |
