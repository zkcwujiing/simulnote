# 06 · 开发路线图与里程碑

> **当前阶段：M1 代码已落地并构建通过；模型改为自托管并已跑通全链路；M0 的探针页已写好并随站点部署，但 8 个探针一个都还没在真机上跑过。**
>
> 也就是说：**「代码能构建、能本地运行、模型能从本站加载」已经证明，「在真实手机上跑不跑得动」还没有任何数据。**
> 下面 M0 一节因此仍然是最优先的事 —— 它决定手机端最终长什么样。
>
> ⚠️ **M1 末发生了一次架构级变更**：Hugging Face 在这条网络线上实测 **0/3 不通**，
> 「浏览器直接下模型」的方案会让站点变成砖，所以改成**模型随站点自托管**。
> 完整的前因后果见 §6.0.1 与 [`07`](07-风险与对策.md) R15。

### 6.0.1 M1 末的架构级变更：模型从「CDN 直下」改为「随站点自托管」

**触发原因**（实测，不是猜测）：

| 目标 | 结果 |
|---|---|
| `https://huggingface.co` | **0/3 成功** —— DNS 被污染成 `59.188.250.54` 这类无效地址，TCP 443 不通 |
| `cdn-lfs.huggingface.co`（权重真正所在） | TCP 443 **不通** |
| `hf.co` | TCP 通，但真实请求 `…/resolve/main/config.json` **超时**（SNI 阻断） |
| `https://hf-mirror.com` | 10/10 成功（只当构建期的下载源） |
| 本机代理 | `ProxyEnable=0`、各种 `*_PROXY` 全空、hosts 无相关条目 —— **干净直连** |

后果不是「慢」，而是**部署成功、打开是砖**：卡在「正在加载模型」，最后退化成「只转写、不翻译」，
与原始需求（英译中）直接冲突。

**改了什么**：

1. 新建 `scripts/fetch-models.mjs`（`pnpm fetch-models`）：构建期把 **24 个文件 / 159.6 MB**
   从 hf-mirror → HF 依次尝试下到 `public/models/`。文件大小**以 tree API 为准**（HEAD 的 `Content-Length` 实测不可信）。
2. 新建 `src/lib/modelSource.ts`：`configureModelSource(env)` 设
   `allowLocalModels=true` / **`allowRemoteModels=false`** / `useBrowserCache=true`，
   `localModelPath = BASE_URL + 'models/'`。**`allowRemoteModels=false` 是护栏**：缺文件就立刻报错。
   ASR 与 MT 引擎、以及探针页的 bench 都改成调它。
3. 模型清单**砍到只剩两个**（自托管下每多一个候选就多一份必须发的体积）：
   `Xenova/whisper-tiny.en`（42 MB，MIT）、`Xenova/opus-mt-en-zh`（117 MB，Apache-2.0）。
4. `pnpm build` 变成 `fetch-models --check && tsc -b && vite build` —— 离线体检拦住「忘了拉模型就构建」
   （pnpm 7+ 不自动跑 pre/post 脚本）。
5. `scripts/check-zero-cost.mjs` 的允许清单**删掉全部 Hugging Face 主机** —— 运行时真的一个外部主机都不碰。
6. `public/models/` 进 `.gitignore`（仓库保持几百 KB，push 不会因跨境丢包反复失败），
   由 Actions 用 `actions/cache/restore|save` 缓存（**不用 `actions/cache@v4`**：fetch 中途失败时绝不能把残缺目录写进缓存）。

**代价（已写进 [`08`](08-零成本方案与分享方式.md) §8.5 / R15）**：站点从约 5 MB 涨到 **186.28 MB / 43 个文件**，
GitHub Pages 的 100 GB/月带宽 ≈ **550 次完整首访/月**，从「不会超」变成了**要盯的指标**。
退路是把 `models/` 挪到 Cloudflare R2（出网免费），**只改 `src/lib/modelSource.ts` 一处**，仍然零成本。

**收益**：`allowRemoteModels=false` 之后，「朋友能不能用」不再取决于他能否连上 Hugging Face ——
这对一个要「发给朋友用」的项目是决定性的。


**下一步（按优先级）**：

1. **在真机上跑探针，尤其是 V8（手机内存）** —— 只有它能回答「手机端到底该用哪种形态」。
   做法：手机直接打开 <https://zkcwujiing.github.io/simulnote/probe.html>（站点已在线），
   或本地 `pnpm dev` 后开 `http://localhost:5173/probe.html`。跑完点「复制报告」，
   把结果落成 `docs/results/V*.md`（见 [`results/README.md`](results/README.md)）。
2. ~~推仓库、开 Pages、部署上线~~ ✅ **已完成**（2026-xx，仓库 `zkcwujiing/simulnote`）。
   剩余动作只有一个：**把链接发给一个真朋友试一次**（M5 的判据就是「朋友能打开并成功用一次」）。
   站点：<https://zkcwujiing.github.io/simulnote/>。CI 每次 push 自动重建，命中模型缓存后约 2 分钟。
   操作步骤见 [`10-上线清单.md`](10-上线清单.md)。
3. 根据真机数据回头调 M2。

## 6.2 M0 · 可行性验证（必须最先做）

每个探针都是**一个独立的最小 demo 页**，只回答一个问题，不做 UI 美化。

| 编号 | 探针问题 | 方法 | 判定标准（通过线） | 不合格时的退路 |
|---|---|---|---|---|
| **V1** | `sherpa-onnx` WASM 流式英文 ASR 能不能在浏览器真流式跑？ | 载 `sherpa-onnx-wasm-simd` + `zipformer-en` 流式模型，喂 16kHz PCM，测 RTF / 首字延迟 / 内存 | RTF ≤ 0.5（快于实时 2 倍）；首字 ≤ 1.0s；内存 ≤ 400MB | 转 V2 |
| **V2** | `transformers.js` + WebGPU 跑 Whisper 的实时性 | 分别测 `whisper-tiny.en` / `whisper-base.en` 的 WASM 与 WebGPU 后端，分段喂音频 | WebGPU 下 RTF ≤ 0.6 即合格 | 降级为「VAD 断句后一次性识别」的非真流式模式 |
| **V3** | Chrome 内置 Translator API 实测可用性与质量 | 在桌面 Chrome 138+ 上跑 en→zh 平行语料 50 句，人工/自动打分；同时记录不可用设备的比例 | 质量明显优于本地小模型即采纳为桌面档 | 桌面也统一走本地模型，架构少一档 |
| **V4** | `opus-mt-en-zh` / `bergamot` 在 WASM 的质量与速度 | 同 V3 的 50 句语料，测质量 + 单句耗时 + 模型体积 | 质量可用（人读得懂、无明显错译）+ 单句 ≤ 300ms | 换模型（NLLB-600M distilled / m2m100-418M） |
| **V5** | WebLLM 跑 Qwen2.5-1.5B 做中文摘要，质量与速度够不够 | 用 3 段真实英文演讲（各 10 分钟）的转写稿，生成纪要，人工评估 | 要点覆盖率 ≥ 70%，无幻觉编造 | 降到 0.5B；或改「抽取式为主 + 生成式润色」 |
| **V6** | 纯 JS TextRank 抽取式中文摘要的兜底质量 | 同 V5 语料，输出关键句列表 | **precision@K ≥ 70%**（原写「要点覆盖率 ≥ 70%」，见 [`results/V6.md`](results/V6.md) 说明：要点 23 条而 K=5，覆盖率数学上限只有 21.7%，该指标按字面无法达成） | 增强为「关键词加权 + 位置加权」（已做：`sentenceWeight()` 串场/客套降权 + 事实句升权） |
| **V7** | Silero VAD 在 `onnxruntime-web` 的 CPU 占用 | 连续跑 10 分钟音频，测 CPU 占用与是否卡 UI | CPU ≤ 15%，UI 不掉帧 | 降到能量 VAD（纯 JS，精度差但零成本） |
| **V8** | 移动端真实能力边界 | **两段**：① 空设备逐块写入内存到失败（设备上限）；② 把 ASR 与 MT 两条 pipeline **同时驻留**后再逐块写入到失败（真实余量）。每步写 localStorage，被系统杀标签页也能拿回最后一步 | 两个模型同时驻留后**余量 ≥ 256 MB** | 手机上砍掉本地 LLM 摘要，只保留 V6 抽取式 |

**M0 交付物**：`docs/results/V1.md` … `V8.md`，每份含：测试设备、方法、原始数据、结论、对架构的影响。

**M0 的出口条件**：V1–V8 全部有结论，且 ARCHITECTURE 文档 §4.5 的降级表被实测数据修正过一次。

## 6.3 M1 · 最小可跑通链路（先证明「能跑通」）

**目标**：最快速度拿到一个能演示的东西，验证产品闭环，不追求质量和移动端。

选择的引擎组合（全部走「零下载」档）：

| 环节 | 用哪个 | 理由 |
|---|---|---|
| ASR | **Web Speech API**（`webkitSpeechRecognition`） | 零下载、真流式、桌面 Chrome 质量好 |
| MT | **Chrome Translator API** | 零下载（首次语言包）、质量好 |
| SUM | **TextRank 抽取式** | 纯 JS、零依赖、不可能失败 |

任务清单：

1. 项目脚手架：Vite + React + TypeScript + Tailwind，`pnpm dev` 能跑
2. `engines/types.ts` + `registry.ts`：先把接口定死
3. ASR L0：`webSpeechAsr.ts`
4. MT L0：`chromeTranslatorMt.ts`（含 `availability()` 四态处理 + 用户手势触发下载）
5. SUM L3：`textRankSum.ts`
6. `translatorPipeline.ts` 最小版：probe → plan → start → stopAndSummarize
7. UI：`ControlBar` + `TranscriptStream`（先不做虚拟列表）+ `SummaryPanel`
8. 全局错误捕获，保证不白屏

**M1 验收**：桌面 Chrome 打开，说 1 分钟英文，屏幕上出现中文，点击停止后出现中文要点列表。

**M1 的风险点**：Web Speech API 在 Chrome 上实际会把音频送到 Google 服务器。**必须在 UI 上明确标注**，并同时提供「隐私模式（本地引擎）」。这是 M2 要解决的问题。

## 6.4 M2 · 手机可用（工作量最大，风险最高）

**目标**：手机浏览器打开链接 → 完整跑完一次会话。

| 环节 | 手机档 | 说明 |
|---|---|---|
| ASR | **sherpa-onnx WASM 流式**（V1 胜出者） | 必须本地、必须流式（手机没有 Web Speech） |
| MT | **opus-mt-en-zh WASM**（V4 胜出者） | 内置 API 手机不支持 |
| SUM | **TextRank 抽取式** | 手机跑不动 LLM；若 V8 证明 0.5B 能跑，再加 L2 |
| VAD | Silero VAD（V7） | 断句是流式识别的必要前置 |

任务清单（2026/10/8 更新）：

1. ✅ `audio/` 全套：`capture.ts` + `pcm-worklet.js`（重采样 16kHz 单声道 f32）+ `vad.ts`（能量法断句，`endSilenceMs` 700 / `preRollMs` 300 / `maxSpeechMs` 15000）+ `UtteranceSegmenter` 分段；另加 `captureHealthOf()` 把 `AudioContextState` + track `readyState` 映射成四档健康度
2. ⬜ `sherpaOnnxAsr.ts`（WASM 流式）—— **未做，理由见下**
3. ✅ `transformersMt.ts`（opus-mt-en-zh）+ `translatorPipeline` 的 `translationQueue` **批量翻译队列**（不是逐句并发）
4. ✅ `lib/modelSource.ts`：Cache Storage 持久化（自管缓存 `simulnote-models-v1`，分块下载 + 换源续传 + 长度校验），只下一次
5. ✅ 模型常驻与卸载：会话成功后 `pipeline.releaseAsr()` 只卸 ASR、保留 MT（前提已确认：`transformersWhisperAsr.dispose()` 置空后 `init()` 能重来）；整体释放走 `registry.disposeAll()`
6. ✅ 移动端 UI 适配：单栏 + `h-dvh` + `viewport-fit=cover` + `pb-safe`/`pt-safe`；所有按钮 `min-height: 2.75rem`（44px，Apple 建议的最小触点）；`LiveView` 新增**字幕字号三档切换并记住**（`simulnote.subScale.v1`）——手机立在桌上、人离一两米时 15px 看不清
7. ✅ **移动端内存守卫**：`lib/session/memory.ts`（可信度分级 + 趋势）+ `sessionStore` 里 15 秒一次的守卫。**刻意不做自动降档**，理由见下
8. ⬜ 移动端 E2E（Playwright device emulation）—— **未做，理由见下**
9. ✅ 模型下载进度提示（本轮补的）：`DownloadBar` 现在**同时出现在开始页与「准备中」的 LiveView**。原先只有开始页有，一点「开始」界面就切到 LiveView、进度条随之消失，手机上下 150 MB 时只剩一句静态的「正在准备模型与麦克风…」，看起来和卡死没区别
10. ✅ 锁屏中断恢复与会话留痕（原清单里没有，是 M2 目标「完整跑完一次会话」的必要条件）：`lib/session/lifecycle.ts`（`visibilitychange`/`freeze`/`resume`/`pagehide`/`pageshow` 五事件 + 30 秒分级）、`lib/session/draft.ts`（12 小时 TTL、上限 400 句、任何残缺整体作废）、`src/components/SessionRecovery.tsx`

**M2 验收**：iPhone Safari + Android Chrome 各完成一次完整会话；全程无崩溃；模型下载有进度提示。

> **当前状态**：代码侧已就绪，`pnpm verify` 全绿、42 个单测通过。**但验收本身只能在真机上做** —— 这一条无法由开发机代替。

### 两项没有做的，以及为什么

**① `sherpa-onnx` 流式识别（第 2 条）**：`docs/03` 把它选为手机档 ASR，但 **V1 从来没有真机跑过** —— `docs/results/` 里没有 V1 报告。而现有的 `transformers.js` whisper-tiny.en **已经在真 iPhone 上实测通过**（[`results/V2-iPhone.md`](results/V2-iPhone.md)：wasm/q8、10 秒音频推理 2504 ms、**RTF 0.25**，比实时快 4 倍）。也就是说 M2 的目标「完整跑完一次会话」现有引擎就能达到；换 sherpa-onnx 买到的其实是**更低的延迟**（真正的流式出字），代价是多一套 wasm 运行时（约 10~20 MB，还要进零成本允许清单）加一个新引擎实现。**这是个取舍，不是遗漏** —— 留到 M2 真机验收之后再决定，因为如果真机跑下来「延迟高到不能忍」，这个取舍的答案会自己浮出来。

**② 移动端 E2E（第 8 条）**：本仓库没有 Playwright，也没有任何浏览器自动化依赖（见 `package.json` 的 devDependencies）。加 Playwright 意味着拉一个几百 MB 的浏览器下载，而且它模拟不出真机的内存压力、锁屏、Safari 的音频中断 —— 恰好是 M2 最需要验证的那几件事。**已知代价**：没有回归网，改手机相关代码后只能靠真机复测。

### 内存守卫为什么不做「自动降档」（第 7 条）

浏览器**没有**任何 API 能告诉你「还剩多少内存」。`performance.memory` 量的是 JS 堆，而模型权重、`Float32Array` 的后备存储、ORT 的 arena 全在堆外 —— 小米平板上实测 `used 3585.82 MB > limit 1077.65 MB`（[`results/V8-内存探针.md`](results/V8-内存探针.md)），这不是异常，是堆外分配的正常表现。**建立在不可信读数上的自动降档，比不降档更糟**：它会在内存其实充足时把用户降级。所以 `memory.ts` 只做两件事 —— 读数不可信时返回 `null` 而不是拿 0 冒充，以及在「高频区间 + 确实在涨」时提醒用户；真正省内存的动作（`releaseAsr()`）放在**会话成功结束**这个语义明确的时间点上。

**M2 的最大不确定性**：手机上同时常驻 ASR + MT 两个模型是否 OOM。**这是整个项目最大的技术风险**（见 [07 文档](07-风险与对策.md) R1）。

> **2026/10/8 更新**：V8 探针在**小米平板**上四次复测，两个模型同时驻留后仍能再分配 **≥ 5120 MB**（撞的是探针自身上限，不是设备上限），平板侧 R1 已证否。平板内存普遍大于手机，**所以手机侧仍然未知**，但「两个 q8 小模型同时驻留 ≈ 150 MB 权重」这个量级本身就远小于任何现代手机的内存，风险主要落在 ORT 的 arena 上而不是权重上。
>
> 退路「分时复用」已在代码里留好了钩子：`pipeline.releaseAsr()` 可以在保留 MT 的前提下单独卸掉 ASR（`dispose()` 后 `init()` 能重来）。现在它挂在「会话成功结束」上；**如果真机上出现 OOM，把它挪到「每段识别完就卸」只是改一行调用点的事。**

## 6.9 建议的开工顺序

```
M0（探针）───┬──▶ M1（桌面最小闭环）───▶ M4 部分（精修+虚拟列表）
             │                                    │
             └──▶ M2（移动端）────────────────────┴──▶ M3（纪要质量）──▶ M4 剩余 ──▶ M5（上线）
```

**先 M1 后 M2 的理由**：M1 只需 3–4 天就能拿到可演示的东西，能最早验证「产品形态对不对」。M2 是 2–3 周的大工程，在方向被确认之前不该先投入。

**M3 放在 M2 之后的理由**：摘要是差异化功能，但它的质量依赖精修后的转写质量；而转写质量取决于 M2 的 ASR 选型。先定 ASR 再优化摘要，避免白做。
