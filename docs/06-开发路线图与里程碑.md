# 06 · 开发路线图与里程碑

> **当前阶段：M1 代码已落地并构建通过，但 M0 的 8 个真机探针一个都还没跑。**
>
> 也就是说：**「代码能构建、能本地运行」已经证明，「在真实手机上跑不跑得动」还没有任何数据。**
> 下面 M0 一节因此仍然是最优先的事 —— 它决定手机端最终长什么样。

## 6.0 实际进度（截至本次交付）

| 里程碑 | 状态 | 说明 |
|---|---|---|
| M0 可行性验证 | ⬜ **未开始** | 8 个探针 V1–V8 一个都没跑；**当前最大的未知** |
| M1 最小可跑通链路 | ✅ **代码完成** | 采集 / 断句 / 两种 ASR / 两种 MT / 抽取式摘要 / 决策降级 / 完整 UI / 导出 / 分享二维码，`pnpm build` 通过（`tsc -b` 无错误） |
| M2 手机可用 | 🟡 部分 | 已做：手机默认改用 WASM + q8（不开 WebGPU，见 `src/lib/device.ts`）、虚拟列表防止长会话卡顿、安全区适配。**未做**：真机实测、锁屏中断恢复、长时间会话内存回收 |
| M3 纪要质量 | 🟡 部分 | 抽取式摘要（TextRank + MMR）与数字抽取已落地；生成式摘要未做（需要几百 MB–几 GB 模型，留到 M6） |
| M4 体验打磨 | 🟡 部分 | Markdown / 纯文本导出、复制、系统分享、二维码已做；PWA 离线、精修未做 |
| M5 部署 | 🟡 配置就绪 | 两个 workflow 已写好；**需要一个 GitHub 仓库和两个 secret 才能真正跑**。Cloudflare 侧受 25 MiB 限制（见 [`07`](07-风险与对策.md) R13） |
| M6 可选增强 | ⬜ 未开始 | — |

**下一步（按优先级）**：

1. **跑 M0 探针，尤其是 V8（手机内存）** —— 只有它能回答「手机端到底该用哪种形态」。
2. **推仓库、配 secret、部署上线**，把两个链接发给一个真朋友试一次（M5 的判据就是「朋友能打开并成功用一次」）。
3. 根据真机数据回头调 M2。

## 6.1 里程碑总览

| 里程碑 | 名称 | 产出 | 预估工作量 | 关键判据 |
|---|---|---|---|---|
| **M0** | 可行性验证（探针） | 8 份实测报告 | 2–3 天 | 每个环节至少有**一个**引擎可用 |
| **M1** | 最小可跑通链路 | 能用的桌面版 | 3–4 天 | 说英文 → 看到中文 → 拿到纪要，全流程通 |
| **M2** | 手机可用 | 移动端降级链路 | 2–3 周 | 手机浏览器打开能完整跑完 |
| **M3** | 纪要质量达标 | 结构化摘要 | 4–6 天 | 摘要可用率 ≥ 80% |
| **M4** | 体验打磨 | 精修 / 导出 / PWA | 4–6 天 | 验收标准 §1.5 全部满足 |
| **M5** | 部署与分享 | 线上链接 + 二维码 | 1–2 天 | 朋友能打开并成功用一次 |
| **M6** | 可选增强 | BYOK / 文件模式 / 说话人 | 按需 | — |

**M0 单独拎出来先做**，因为整个架构的地基是「浏览器到底跑不跑得动这些模型」。这几个数字一旦不成立，架构要改，越晚发现代价越大。

## 6.2 M0 · 可行性验证（必须最先做）

每个探针都是**一个独立的最小 demo 页**，只回答一个问题，不做 UI 美化。

| 编号 | 探针问题 | 方法 | 判定标准（通过线） | 不合格时的退路 |
|---|---|---|---|---|
| **V1** | `sherpa-onnx` WASM 流式英文 ASR 能不能在浏览器真流式跑？ | 载 `sherpa-onnx-wasm-simd` + `zipformer-en` 流式模型，喂 16kHz PCM，测 RTF / 首字延迟 / 内存 | RTF ≤ 0.5（快于实时 2 倍）；首字 ≤ 1.0s；内存 ≤ 400MB | 转 V2 |
| **V2** | `transformers.js` + WebGPU 跑 Whisper 的实时性 | 分别测 `whisper-tiny.en` / `whisper-base.en` 的 WASM 与 WebGPU 后端，分段喂音频 | WebGPU 下 RTF ≤ 0.6 即合格 | 降级为「VAD 断句后一次性识别」的非真流式模式 |
| **V3** | Chrome 内置 Translator API 实测可用性与质量 | 在桌面 Chrome 138+ 上跑 en→zh 平行语料 50 句，人工/自动打分；同时记录不可用设备的比例 | 质量明显优于本地小模型即采纳为桌面档 | 桌面也统一走本地模型，架构少一档 |
| **V4** | `opus-mt-en-zh` / `bergamot` 在 WASM 的质量与速度 | 同 V3 的 50 句语料，测质量 + 单句耗时 + 模型体积 | 质量可用（人读得懂、无明显错译）+ 单句 ≤ 300ms | 换模型（NLLB-600M distilled / m2m100-418M） |
| **V5** | WebLLM 跑 Qwen2.5-1.5B 做中文摘要，质量与速度够不够 | 用 3 段真实英文演讲（各 10 分钟）的转写稿，生成纪要，人工评估 | 要点覆盖率 ≥ 70%，无幻觉编造 | 降到 0.5B；或改「抽取式为主 + 生成式润色」 |
| **V6** | 纯 JS TextRank 抽取式中文摘要的兜底质量 | 同 V5 语料，输出关键句列表 | 至少能挑出真正重要的句子（人工判断 ≥ 60% 命中） | 增强为「关键词加权 + 位置加权」 |
| **V7** | Silero VAD 在 `onnxruntime-web` 的 CPU 占用 | 连续跑 10 分钟音频，测 CPU 占用与是否卡 UI | CPU ≤ 15%，UI 不掉帧 | 降到能量 VAD（纯 JS，精度差但零成本） |
| **V8** | 移动端真实能力边界 | iPhone Safari + Android Chrome 上测：WebGPU 有无、CacheStorage 配额、可加载的最大模型、页面 OOM 阈值 | 至少能同时跑通「ASR + MT」不 OOM | 手机上砍掉本地 LLM 摘要，只保留 V6 抽取式 |

**M0 交付物**：`docs/results/V1.md` … `V8.md`，每份含：测试设备、方法、原始数据、结论、对架构的影响。

**M0 的出口条件**：V1–V8 全部有结论，且 ARCHITECTURE 文档 §4.5 的降级表被实测数据修正过一次。

## 6.3 M1 · 最小可跑通链路（先证明「能跑通」）

**目标**：最快速度拿到一个能演示的东西，验证产品闭环，不追求质量和移动端。

选择的引擎组合（全部走「零下载」档）：

| 环节 | 用哪个 | 理由 |
|---|---|---|
| ASR | **Web Speech API**（`webkitSpeechRecognition`） | 零下载、真流式、桌面 Chrome 质量好 |
| MT | **Chrome Translator API** | 零下载（首次语言包）、质量好 |
| SUM | **TextRank 抽取式** | 纯 JS、零依赖、不可能失败 |

任务清单：

1. 项目脚手架：Vite + React + TypeScript + Tailwind，`pnpm dev` 能跑
2. `engines/types.ts` + `registry.ts`：先把接口定死
3. ASR L0：`webSpeechAsr.ts`
4. MT L0：`chromeTranslatorMt.ts`（含 `availability()` 四态处理 + 用户手势触发下载）
5. SUM L3：`textRankSum.ts`
6. `translatorPipeline.ts` 最小版：probe → plan → start → stopAndSummarize
7. UI：`ControlBar` + `TranscriptStream`（先不做虚拟列表）+ `SummaryPanel`
8. 全局错误捕获，保证不白屏

**M1 验收**：桌面 Chrome 打开，说 1 分钟英文，屏幕上出现中文，点击停止后出现中文要点列表。

**M1 的风险点**：Web Speech API 在 Chrome 上实际会把音频送到 Google 服务器。**必须在 UI 上明确标注**，并同时提供「隐私模式（本地引擎）」。这是 M2 要解决的问题。

## 6.4 M2 · 手机可用（工作量最大，风险最高）

**目标**：手机浏览器打开链接 → 完整跑完一次会话。

| 环节 | 手机档 | 说明 |
|---|---|---|
| ASR | **sherpa-onnx WASM 流式**（V1 胜出者） | 必须本地、必须流式（手机没有 Web Speech） |
| MT | **opus-mt-en-zh WASM**（V4 胜出者） | 内置 API 手机不支持 |
| SUM | **TextRank 抽取式** | 手机跑不动 LLM；若 V8 证明 0.5B 能跑，再加 L2 |
| VAD | Silero VAD（V7） | 断句是流式识别的必要前置 |

任务清单：

1. `audio/` 全套：`capture.ts` + `resampler.worklet.ts`（重采样 16kHz 单声道 f32）+ `vad.ts`（0.35s 断句 / 0.8s 预滚 / 12s 最长）+ `segmenter.ts`
2. `sherpaOnnxAsr.ts`：接 WASM 流式识别，实现 `onPartial` / `onFinal`
3. `opusMtWasm.ts`：接 transformers.js 或 bergamot，做**批量翻译队列**（不是逐句并发）
4. `modelCache.ts`：Cache Storage 持久化模型，只下一次
5. `lru.ts`：模型常驻 LRU，手机内存吃紧时卸载
6. 移动端 UI 适配：单栏、大按钮、字幕字号自适应、`viewport-fit=cover`
7. **移动端内存守卫**：`performance.memory` / OOM 前主动降档
8. 移动端 E2E 测试（Playwright device emulation）

**M2 验收**：iPhone Safari + Android Chrome 各完成一次完整会话；全程无崩溃；模型下载有进度提示。

**M2 的最大不确定性**：手机上同时常驻 ASR + MT 两个模型是否 OOM。**这是整个项目最大的技术风险**（见 [07 文档](07-风险与对策.md) R1）。若确实不行，退路是「分时复用」——识别完一段后卸载 ASR 再加载 MT，代价是延迟上升。

## 6.5 M3 · 纪要质量达标（差异化功能）

**目标**：把「总结要点」从「能用」做到「好用」。

任务清单：

1. `sum/summarizer.ts`：三段式流程（chunk 摘要 → 全局归并 → 结构化成稿）
2. `webllmSum.ts`：接 WebLLM Qwen2.5-1.5B-Instruct q4f16，流式输出
3. `factsExtractor.ts`：**从英文原文**抽数字、日期、专有名词、百分比（不经翻译——hayamimi 的教训是「小模型翻译数字不可靠」，所以数字走原文抽取 + 对照表）
4. `transformersSum.ts`：0.5B 兜底档（若 V8 证明手机可跑）
5. 摘要流式渲染到 `SummaryPanel`
6. 输出模板落地：主题 / 速览 / 要点 / 关键数字表 / 结论与待办
7. `tests/unit/factsExtractor.test.ts`：数字抽取必须有单测（这是最容易错的点）

**M3 验收**：用 3 段真实英文演讲测试，要点覆盖率 ≥ 70%，数字保留准确率 ≥ 95%（因为走了原文抽取），无幻觉编造。

**设计要点**：摘要模块的输入用**精修后的转写**，不是 live 结果。所以 M3 依赖 M4 的精修，或先做 M4 再做 M3。

## 6.6 M4 · 体验打磨

| 任务 | 说明 |
|---|---|

## 6.8 M6 · 可选增强（不在承诺范围内）

- BYOK：允许用户填自己的 API Key（**默认关闭**，UI 明确提示「只存在你自己的浏览器」）
- 说话人分离（`sherpa-onnx` 有 CAM++ 模型）
- 双向对话模式（中英互译）
- 多人共看房间（**会引入服务器成本，与零费用冲突，需需求方明确同意才做**）

## 6.9 建议的开工顺序

```
M0（探针）───┬──▶ M1（桌面最小闭环）───▶ M4 部分（精修+虚拟列表）
             │                                    │
             └──▶ M2（移动端）────────────────────┴──▶ M3（纪要质量）──▶ M4 剩余 ──▶ M5（上线）
```

**先 M1 后 M2 的理由**：M1 只需 3–4 天就能拿到可演示的东西，能最早验证「产品形态对不对」。M2 是 2–3 周的大工程，在方向被确认之前不该先投入。

**M3 放在 M2 之后的理由**：摘要是差异化功能，但它的质量依赖精修后的转写质量；而转写质量取决于 M2 的 ASR 选型。先定 ASR 再优化摘要，避免白做。
