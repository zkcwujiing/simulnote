# 08 · 零成本方案与分享方式

> 本文件回答两个问题：**怎么保证一分钱不花**，以及**怎么把链接发给朋友**。
> 其中第二大节（国内访问）是一个必须由需求方知情的硬矛盾，请重点看。

## 8.1 成本来源清单（逐项归零）

| 成本项 | 常规做法 | 本项目的做法 | 成本 |
|---|---|---|---|
| 服务器 / 计算 | 云服务器跑 ASR + 翻译模型 | **全部在用户浏览器里算**（WASM / WebGPU） | ¥0 |
| 推理 API | OpenAI / Deepgram / Azure 按量计费 | **不调用任何付费 API** | ¥0 |
| 数据库 / 存储 | 云端存转写记录 | **IndexedDB 存在用户本机** | ¥0 |
| 静态托管 | 买主机 / 买 CDN | GitHub Pages 或 Cloudflare Pages 免费额度 | ¥0 |
| 域名 | 买域名（约 ¥30–60/年） | **用平台自带的免费子域名** | ¥0 |
| HTTPS 证书 | 买证书 | 平台自动签发（Let's Encrypt / 平台证书） | ¥0 |
| 模型权重 | 自己训练 / 买 API | 用 Hugging Face 上开源免费模型（Apache-2.0 / MIT） | ¥0 |
| 模型分发 | 自己搭 CDN | **构建期拉进 `public/models/`，随站点一起发**（见 8.3；运行时零外部依赖） | ¥0 |
| 账号体系 | 自建鉴权服务 | **不做账号** | ¥0 |
| 短信 / 邮件 | — | 不做 | ¥0 |

**唯一可能在将来产生费用的东西**：任何「服务端组件」。所以把「**无服务端**」定为架构铁律（见 [04 文档](04-系统架构设计.md)）。

## 8.2 ⚠️ 硬矛盾：零成本 vs 国内朋友的访问稳定性

这是本方案里**唯一无法用技术手段完全解决的问题**，必须让需求方知情。

### 事实

| 托管方案 | 免费额度 | 默认域名 | 中国大陆访问 |
|---|---|---|---|
| **GitHub Pages** | 站点 ≤1GB；**软**带宽 100GB/月；软限制 10 次构建/小时 | `用户名.github.io/仓库名` | ⚠️ **不稳定**，常见间歇性无法访问、加载慢 |
| **Cloudflare Pages** | 构建 500 次/月；**文件数 ≤20,000**；**单文件 ≤25 MiB**；带宽不计量 | `项目名.pages.dev` | ⚠️ **常被判定不可访问**（官方社区有专门讨论：[Cloudflare Pages is inaccessible in China](https://community.cloudflare.com/t/cloudflare-pages-is-inaccessible-in-china/777481/3)） |
| **腾讯 EdgeOne Pages（中国站）** | 有免费额度 | 项目域名 | 🔴 **默认域名有 3 小时有效期！**「项目加速区域为中国大陆可用区或全球含中国大陆时，须使用系统生成的预览链接访问，**该链接有效期为 3 小时，超时后返回 401**」（[官方文档](https://edgeone.cloud.tencent.com/pages/document/175191784523485184)）。要稳定访问必须绑自定义域名，而**绑国内加速的域名需要工信部备案**。 |
| **腾讯 EdgeOne Pages（国际站）** | 有免费额度 | `*.edgeone.app` | 默认域名全球可用，但国内延迟取决于边缘节点 |

### 结论

> **「完全免费」+「国内朋友点开就能稳定访问」这两个条件，目前无法同时满足。**
>
> 想稳定 → 要自定义域名（约 ¥30–60/年）+ 工信部备案（备案本身免费，但需 1–3 周、需国内服务商主体、且要有域名）。
>
> 想零成本 → 只能用平台默认域名，接受国内访问**时通时不通**。

### 三条可选路线（请需求方选一条）

| 路线 | 做法 | 成本 | 风险 |
|---|---|---|---|
| **A. 纯零成本，多平台兜底**（建议默认） | 同一份构建同时部署到 GitHub Pages + Cloudflare Pages，给朋友**两个链接**，哪个能打开用哪个；再提供二维码 | ¥0 | 某些网络环境下两个都打不开 |
| **B. 国内稳定优先** | 自购域名 + 备案 + EdgeOne Pages 国内加速 | 约 ¥30–60/年 | 破坏零成本承诺；备案需 1–3 周 |
| **C. 折中** | 主站部署到 Cloudflare Pages（默认域名永久有效、全球可用），国内访问慢时改用 B 的域名做跳板 | 视是否买域名 | 部分解决 |

**我的建议**：先做 **A**，把项目跑起来、验证产品价值。如果朋友反馈「打不开」的比例高，再花那 ¥50 上 B。**不要为了还没验证的产品先买域名。**

### 另一个被排除的方案：本地打开 HTML 文件

「把 zip 发给朋友，双击 `index.html`」看起来零成本且无需部署，但**行不通**：

1. `file://` 协议**不是安全上下文**，`getUserMedia`（麦克风）会被浏览器直接拒绝；
2. ES Module 在 `file://` 下有 CORS 限制；
3. 若要用多线程 WASM，需要 `Cross-Origin-Opener-Policy` / `Cross-Origin-Embedder-Policy` 响应头，`file://` 无法设置。

**所以必须有一个 HTTPS 的静态站。** 好在这不需要花钱。

## 8.3 模型分发方案（也必须是零成本）

**最终结论：模型自托管 —— 和站点一起发布，运行时零外部依赖。**
（原方案是「浏览器直接去 Hugging Face 下」，实测在国内这条线上 0/3 完全不通，
站点会变成砖，见 8.3.1。实现细节见 [`09`](09-本地运行与部署.md) §9.7。）

模型合计 **159.6 MB**（whisper-tiny.en 42.4 MB + opus-mt-en-zh 117.2 MB），
这部分流量是最大的成本风险。

| 方案 | 说明 | 结论 |
|---|---|---|
| **自托管到同一个静态站**（**采用**） | 构建期由 `scripts/fetch-models.mjs` 拉进 `public/models/`，随站点发布 | ✅ GitHub Pages **没有单文件上限**，是唯一无损路线；代价是首访多下 160 MB |
| Hugging Face CDN | `https://huggingface.co/{repo}/resolve/{revision}/{file}` | ❌ **已排除**：实测 0/3 不通，见 8.3.1 |
| 国内 HF 镜像（hf-mirror.com） | 只作为**构建期**的下载源 | ⚠️ 不进运行时白名单 —— 可用性押在第三方镜像的善意上 |
| Cloudflare R2 | 约 10GB 存储 + 出网流量免费 | 备选：真放量时把 `models/` 挪过去，只改 `src/lib/modelSource.ts` 一处 |
| jsDelivr | 镜像 GitHub / npm 上的文件 | ❌ 有单文件大小限制，大模型不行；且实测请求被重置 |
| **Cache Storage（本地）** | 模型加载后由 transformers.js 存进浏览器 Cache Storage | ✅ **每个用户只下一次**，这是把流量成本压到最低的关键 |

### 8.3.1 为什么排除了 Hugging Face CDN（2026 实测）

| 目标 | 结果 |
|---|---|
| `https://huggingface.co` | **0/3 成功** —— DNS 被污染成 `59.188.250.54` 这类无效地址，TCP 443 不通 |
| `cdn-lfs.huggingface.co`（权重就在这） | TCP 443 **不通** |
| `hf.co` | TCP 通，但真实请求 `…/resolve/main/config.json` **超时**（SNI 阻断） |
| `https://hf-mirror.com` | 10/10 成功（只当构建期的下载源用） |
| `https://pages.github.com` | 10/10 成功 |
| 本机代理设置 | `ProxyEnable=0`、`HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 全空、hosts 无相关条目 —— **就是干净直连** |

「浏览器直接下模型」的后果不是慢，而是**站点能部署成功、打开却是砖**：
卡在「正在加载模型」，最后退化成「只转写、不翻译」。这和原始需求直接冲突。

**关键设计**：

1. 模型**只在首次使用时加载**，之后永久缓存；
2. **分层加载**：先加载小的 ASR 模型让用户立刻看到效果，翻译模型后台预下载；
3. 明确显示加载进度与体积；
4. **不做**「轻量模式」削减功能 —— 模型已经压在 160 MB，再砍就只剩转写了。
   真正需要省流量时，改用「最快启动」档（浏览器原生识别，零下载）。

## 8.4 分享方式设计

验收标准 §1.5-5 要求：**一个 URL + 一个二维码**。

| 分享方式 | 实现 | 成本 |
|---|---|---|
| 复制链接 | 一个按钮，`navigator.clipboard.writeText` | ¥0 |
| 二维码 | 纯前端生成（`qrcode` 库），不调用任何在线 QR 服务 | ¥0 |
| IM 预览卡片 | `og-image.png` + `<meta property="og:*">`，构建期由 `VITE_SITE_URL` 补成**绝对地址**（相对路径微信/TG 基本不解析） | ¥0 |
| 手机主屏 | PWA `manifest.webmanifest` + `apple-touch-icon.png`（iOS 不认 SVG 作主屏图标） | ¥0 |

**故意不做的事**：不做邀请码、不做「对方必须先注册」、不做登录墙。朋友点开就能用，这是 P0 需求 F6 的核心。

## 8.5 免费额度边界（什么时候会不够用）

| 资源 | 免费额度 | 本项目的实际用量估算 | 是否会超 |
|---|---|---|---|
| GitHub Pages 站点体积 | 1 GB | **186.28 MB / 43 个文件** | ❌ 尚有 5 倍余量 |
| GitHub Pages 带宽 | 100 GB/月（软限制） | **每次完整首访 186 MB ≈ 550 人次/月**；复访不花带宽（Cache Storage 命中） | ⚠️ **模型自托管之后，这条从「不会超」变成了要盯的指标** |
| Cloudflare Pages 文件数 | 20,000 | 43 个 | ❌ 不会 |
| Cloudflare Pages 单文件 | 25 MiB | ⚠️ **4 个文件超限**（ORT wasm 25.62 MiB + 三个模型 `.onnx` 29–57 MiB），见 R13 | ❌ 这条路暂时走不通 |
| Cloudflare Pages 构建次数 | 500 次/月 | 一天改 15 次才用完 | ❌ 不会 |
| 模型下载源（hf-mirror / HF） | 无限但有限速 | **只在构建期用一次**，之后进 Actions 缓存 | ❌ 不会 |
| 用户侧磁盘 | 浏览器 Cache Storage 配额 | 桌面通常给到磁盘的 60%；手机更紧 | ⚠️ 手机端需 `navigator.storage.estimate()` 检查 |

**要盯的规模性风险变了**：不再是「HF CDN 限速」，而是 **GitHub Pages 那 100 GB/月**。
如果链接被大量转发（几千人首次打开），会先把带宽用完 —— 到那时把 `models/` 挪到
Cloudflare R2（出网免费）即可，只改 `src/lib/modelSource.ts` 一处，**仍然零成本**。

## 8.6 零成本自检清单（上线前逐项打勾）

- [ ] 代码里没有任何付费 API 的 endpoint（`api.openai.com` / `api.deepgram.com` / `*.azure.com` 等）
- [ ] 没有任何硬编码的密钥（构建产物里 grep 一遍 `sk-`、`api_key`）
- [ ] 没有引入任何分析/埋点 SDK（Google Analytics、Sentry 云端等）
- [ ] 没有服务端组件、没有数据库、没有需要常驻的进程
- [ ] 托管平台用的是免费计划，且已确认不绑信用卡自动升级
- [ ] 模型来源全部是开源免费授权（Apache-2.0 / MIT 等，逐个核对），不使用 CC BY-SA 传染性授权的模型
  （当前两个：`Xenova/whisper-tiny.en` 来自 OpenAI Whisper，MIT；`Xenova/opus-mt-en-zh` 来自 Helsinki-NLP，Apache-2.0）
- [ ] 所有资源（字体、图标）都是本地或免费 CDN，没有需要付费授权的素材
- [ ] README 里写明「如将来加入任何需要服务器的功能，将破坏零成本承诺」

## 8.7 已落地的部署实现（路线 A）

需求方已选定 **路线 A：同一份构建双部署**。实现与操作步骤见 [`09-本地运行与部署.md`](09-本地运行与部署.md)，要点：

- `.github/workflows/deploy-pages.yml` → GitHub Pages，构建时注入 `VITE_BASE=/<仓库名>/`（项目站子路径）。
  它还会在构建前跑 `pnpm fetch-models` 把 159.6 MB 模型拉下来（并用 `actions/cache/restore|save`
  缓存，保证失败时不会写进残缺缓存），**这一步就是「运行时零外部依赖」的实现方式**。
- `.github/workflows/deploy-cloudflare.yml` → Cloudflare Pages，`base` 用 `/`。
  ⚠️ **暂时跑不通**：模型自托管后产物里有 4 个文件超过它的 25 MiB 单文件上限。见 R13。
- 网站内置「分享」按钮，**在本机**用 `qrcode` 生成二维码（`src/components/ShareCard.tsx`），不走任何在线二维码服务。
- `scripts/check-zero-cost.mjs`（`pnpm lint:cost`）机械校验：源码里出现的每个外部主机都必须在允许清单内，且不得出现形似密钥的字符串。
  **模型自托管之后，允许清单里已经删掉了 `huggingface.co` / `hf.co`** —— 运行时真的一个外部主机都不碰。
- `scripts/check-upload-size.mjs`（`pnpm lint:size`）在 CI 里提前拦下超过 25 MiB 的文件，并给出解决办法（见 R13）。
- `scripts/fetch-models.mjs`（`pnpm fetch-models`）负责把模型拉到 `public/models/`；
  `pnpm build` 的第一步 `fetch-models --check` 会拦住「忘了拉模型就构建」的情况。

## 8.8 一句话总结

> **零成本是可行的**，因为所有 AI 计算都在用户自己的浏览器里跑，托管只是一个免费的静态文件服务。
>
> **模型也自己托管**：构建期拉一次、随站点发出，运行时**不访问任何外部服务** ——
> 所以「朋友能不能用」不再取决于他能不能连上 Hugging Face。
>
> **但请需求方知悉**：零成本的代价是「国内朋友的访问稳定性不保证」。这是平台能力边界，不是实现问题。
> 而且模型自托管之后，GitHub Pages 的 100 GB/月带宽成了要盯的指标（≈550 次完整首访/月）。
