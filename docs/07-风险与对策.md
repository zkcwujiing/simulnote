# 07 · 风险与对策

> 每条风险给出：**触发信号**（怎么知道它要发生了）、**影响**、**对策**、**退路**。
> 风险等级：🔴 可能让项目失败 / 🟡 会显著影响体验 / 🟢 可控。

## 一、技术风险

### R1 🔴 手机端内存不足（最大风险）

**内容**：手机上同时常驻 ASR 模型 + 翻译模型，可能直接被浏览器杀进程（iOS Safari 尤其严格，标签页内存上限约 1–1.5GB）。

**触发信号**：M0 的 V8 探针中，加载第二个模型时页面刷新或崩溃；或 `performance.memory.usedJSHeapSize` 逼近上限。

**影响**：项目核心承诺（手机可用）落空，退化为桌面工具。

**对策**：
1. **V8 必须先做**，在写任何业务代码之前拿到真实数字。
2. 模型量化到 int8 / q4，控制单模型体积。
3. 实现 `lru.ts` 模型常驻管理，借鉴 hayamimi `--max-resident` 的思路。
4. 移动端默认使用**最小模型组合**（whisper-tiny.en + opus-mt tiny）。

**退路（按优先级）**：
- 退路 A：**分时复用**——VAD 断句后卸载 ASR，加载 MT 翻译，译完再切回。延迟上升约 0.5–1s，但内存峰值减半。
- 退路 B：手机上砍掉本地 LLM 摘要，只用 TextRank 抽取式（内存占用几乎为零）。
- 退路 C：手机上**只做「上传音频文件 → 转写 + 翻译 + 纪要」**，不做实时。功能弱化但依然可用、依然零成本。

### R2 🔴 Web Speech API 的隐私与可用性双重问题

**内容**：Chrome 的 `webkitSpeechRecognition` 在多数实现里会把音频送到 Google 服务器，与「音频不出设备」的隐私承诺冲突；且它只在 Chrome/Edge 可用，**iOS 上 Chrome 用的是 WebKit 内核，能力与 Safari 一致，行为不可控**。

**触发信号**：M1 实测发现 Web Speech 在 iOS 或 Firefox 上完全不可用。

**对策**：
1. UI 上**明确标注**「快速模式：识别在你的浏览器与识别服务之间进行」字样，绝不隐瞒。
2. 提供「隐私模式（全程本地）」开关。
3. 不把 Web Speech 当作唯一 L0 档——注册表里它只是**优先项**，探测失败立刻降级。

**退路**：把 Web Speech 从关键路径移除，L0 直接就是本地 WASM 模型。代价是首次打开要下载模型，体验变重。

### R3 🟡 Chrome 内置 Translator API 门槛过高

**内容**：要求 ≥22GB 可用磁盘、16GB 内存、4 核、4GB VRAM。大量普通笔记本和几乎所有手机都拿不到。

**触发信号**：`Translator.availability()` 返回 `'unavailable'` 的比例超预期。

**对策**：架构上它**只是四层里的一层**，缺失不影响主流程。`probe()` 拿不到就静默降到本地模型档。

**注意**：当 `availability()` 返回 `downloadable` / `downloading` 时，`Translator.create()` **必须由用户手势触发**，否则抛 `NotAllowedError`。所以 UI 上必须有一个「启用增强翻译」按钮 + `downloadprogress` 进度条，不能自动触发。

### R4 🟡 翻译质量不够（尤其数字）

**来源**：hayamimi 官方 Limitations 原文——"numeric values are not reliably preserved"。这是所有小模型的通病。

**影响**：纪要里的数字错了，比没有数字更糟（会误导）。

**对策**：
1. **数字不经翻译链路**：`factsExtractor.ts` 直接从英文原文用正则抽取数字/日期/百分比，附上中文参考译法，在纪要里以**对照表**形式呈现（原文 | 中文 | 出处）。
2. 数字抽取必须有单测（`tests/unit/factsExtractor.test.ts`）。
3. 摘要提示词里明确要求「只使用转写稿中出现的信息，不得编造」。

**退路**：若翻译质量整体不达标，调整为「英文原文完整保留 + 中文译文标注为参考」。

### R5 🟡 模型体积与首次加载体验

**内容**：ASR + MT + SUM 三个模型加起来可能 200–400MB，手机流量下载体验差。

**对策**：
1. **分层加载**：先加载 ASR（用户能立刻看到效果），翻译模型后台预下载。
2. 明确显示剩余体积和网速估算。
3. Cache Storage 持久化——**只下一次**。
4. 提供「轻量模式」（只用 tiny 模型，总量压到 100MB 内）。

### R6 🟢 浏览器兼容性碎片化

**内容**：WebGPU / WebAssembly SIMD / AudioWorklet / CacheStorage 支持度不一。

**对策**：`lib/capability.ts` 统一探测，所有降级判断走它；**绝不写 `if (navigator.gpu)` 这种散落各处的判断**。

### R7 🟢 音频重采样与回声

**内容**：`getUserMedia` 拿到的采样率因设备而异（44.1k / 48k），必须重采样到 16kHz；外放时会有回声被重新拾取。

**对策**：AudioWorklet 做重采样；UI 提示「建议戴耳机」；可选 `echoCancellation: true` 约束。

## 二、产品与需求风险

### R8 🟡 需求方对「实时」的期望与现实不符

**内容**：真正的「同声传译」是毫秒级的。浏览器本地推理的实际延迟是 **1.5–2.5s**。用户可能期待「说完立刻出中文」。

**对策**：
1. 「动态调整」在 01 文档 N1 里把目标定成**首字 ≤1.5s、整句 ≤2.5s**，并让需求方确认。
2. UI 上用 partial（灰色草稿行）给出**即时反馈**，让用户感知到系统在动，缓解等待焦虑。
3. 借鉴 hayamimi 的 two-pass refine：先出粗糙的 live 结果（快），静音后再精修替换（准）。**用「快 + 越来越好」替代「一次性准确」。**

### R9 🟡 范围膨胀

**内容**：调研了 otoji 之后很容易想加「多人房间」「语音图编辑器」，这会把项目从「一个周末能做完的静态站」变成「需要服务器和账号的复杂系统」，直接破坏零费用约束。

**对策**：01 文档 §1.2 C 已明确列出**不做**的事。任何新增需求先问「会不会引入服务器成本」，会就拒绝或后置。

### R10 🟢 「免费」的可持续性

**内容**：GitHub Pages / Cloudflare Pages 免费额度对纯静态站几乎无限；但若将来加了任何服务端组件（房间、云同步），成本立刻出现。

**对策**：把「无服务端」当作架构铁律写进 04 文档。要加服务端功能，必须需求方**明确同意并承担费用**。

## 三、依赖与外部风险

### R11 🟡 上游 API/模型变更

**内容**：
- `Translator` API 仍在快速演进，旧版 `window.ai.translator` **已废弃**，未来说不准还会变。
- transformers.js / sherpa-onnx 的 API 也在动。
- Hugging Face CDN 上的模型文件可能被移除或改名。

**对策**：
1. 引擎层是**可替换实现**——API 变了只改 `engines/mt/chromeTranslatorMt.ts` 一个文件。
2. 关键模型**自托管**（放在自己的静态托管上或固定 revision 的 CDN 地址），不依赖浮动 latest。
3. 锁死依赖版本，不自动升级。

### R12 🟢 许可证合规

**内容**：hayamimi 的 ja→en FuguMT 模型是 **CC BY-SA 4.0**（传染性）。各模型授权不同，仓库通常不含权重。

**对策**：
1. **只用 permissive 许可的模型**（Apache-2.0 / MIT）。
2. 上线前逐个核对模型卡上的 license，写进 `docs/` 记录。
3. 本项目自身用 MIT。

### R13 🔴 ONNX Runtime 的 wasm 超出 Cloudflare Pages 单文件上限（**M1 实测新增**）

**内容**：`transformers.js` v4 会让 Vite 顺带产出

```
dist/assets/ort-wasm-simd-threaded.asyncify-CxOG5pUO.wasm     26,861,777 字节 = 25.62 MiB
```

而 Cloudflare Pages 的**单文件上限是 25 MiB = 26,214,400 字节**。超了 0.62 MB，Cloudflare 会**直接拒绝整次部署**。
GitHub Pages 没有这个限制（站点 ≤1GB），所以「路线 A 双部署」的 Cloudflare 半边会被卡死。

同目录下 ORT 还提供其它变体，但**没有一个是能直接替换的**：

| 文件 | 字节 | 能否用 |
|---|---|---|
| `ort-wasm-simd-threaded.asyncify.wasm` | 26,861,777 | 实际被打进产物的就是这个，超限 |
| `ort-wasm-simd-threaded.jsep.wasm` | 28,352,885 | 更大 |
| `ort-wasm-simd-threaded.jspi.wasm` | 16,811,691 | 不同 ABI，JS 胶水不匹配 |
| `ort-wasm-simd-threaded.wasm` | 14,264,838 | 不同 ABI，JS 胶水不匹配 |

**对策（已落地）**：

1. **首选**：主链接用 GitHub Pages，Cloudflare 那半边可以先不部署 —— 功能完全一样，零成本承诺不受影响。
2. **两个源站都要完整**时：把 wasm 上传为本仓库的 **GitHub Release 资产**（免费、无需付费账号），设置仓库变量 `VITE_ORT_WASM_BASE`，`vite.config.ts` 的 `ortWasmPolicy` 插件据此把超大 wasm 从产物里剔除，运行时由 `src/lib/ortEnv.ts` 交给 ORT 去外部取。
   完整步骤见 [`09-本地运行与部署.md`](09-本地运行与部署.md) §9.4.3。
3. 增加机械闸门 `scripts/check-upload-size.mjs`（`pnpm lint:size`），在 CI 里**上传之前**就报出「哪个文件超了多少、怎么解决」，而不是把云厂商那句没信息量的报错丢给人。
4. 两个开关**必须成对使用**：只删文件不设基址 → 本地模型加载失败；只设基址不删文件 → 上传被拒。

**残余风险**：外置 wasm 引入了两个新的外部主机（`github.com`、`objects.githubusercontent.com`），已同步加进 `scripts/check-zero-cost.mjs` 的允许清单，并注明「这是本项目自己的 Release 资产，不是第三方 API」。

### R14 🟡 构建链在 Windows 上很脆（**M1 实测新增**）

**内容**：下面每一条都真实卡住过构建，且报错信息都指向错误的方向：

| 现象 | 真正原因 |
|---|---|
| `ERR_MODULE_NOT_FOUND: Cannot find package 'rollup'` | Windows 上用 junction 实现链接，Node 的 ESM 解析器不解析 junction。**必须**在 `pnpm-workspace.yaml` 写 `nodeLinker: hoisted`；写进 `.npmrc` 无效（pnpm 11 不读） |
| `spawn EPERM` | 受限沙箱不允许子进程用管道 stdio，esbuild 起不来。与配置无关，换写法无用 |
| `remove C:\...\Temp\esbuild-xxxx: Access is denied` | 把 `TEMP`/`TMP` 指到项目内 `.tmp/` |
| `Cannot apply unknown utility class 'btn'` | Tailwind v4 的 `@apply` 只认工具类，自定义组件类必须写成纯 CSS |
| `ERR_PNPM_IGNORED_BUILDS` | pnpm 11 的 allowlist 在 `pnpm-workspace.yaml` 的 `allowBuilds`，键名和位置都与旧版不同 |

**对策**：
1. 全部写进 [`09-本地运行与部署.md`](09-本地运行与部署.md) §9.3，并在 `pnpm-workspace.yaml`、`vite.config.ts` 的注释里就地说明「为什么」。
2. CI（Ubuntu）上不会遇到第 1–3 条，说明这些是**本地 Windows 环境特有**的，不是代码问题 —— 出问题时先怀疑环境。
3. 提交前统一跑 `pnpm verify`（build + 零成本 + 体积闸门）。

## 四、风险处置优先级（如果只能做三件事）

1. **立刻做 V8（手机内存探针）** —— 它决定项目形态，不确定它就不知道该写什么代码。
2. **数字抽取独立于翻译链路** —— 这是最容易被忽视、代价最高的缺陷。
3. **守住「无服务端」铁律** —— 一旦破坏，零费用承诺立刻失效。
