# 07 · 风险与对策

> 每条风险给出：**触发信号**（怎么知道它要发生了）、**影响**、**对策**、**退路**。
> 风险等级：🔴 可能让项目失败 / 🟡 会显著影响体验 / 🟢 可控。

## 一、技术风险

### R1 🔴 手机端内存不足（最大风险）

**内容**：手机上同时常驻 ASR 模型 + 翻译模型，可能直接被浏览器杀进程（iOS Safari 尤其严格，标签页内存上限约 1–1.5GB）。

**触发信号**：M0 的 V8 探针中，加载第二个模型时页面刷新或崩溃；或 `performance.memory.usedJSHeapSize` 逼近上限。

**影响**：项目核心承诺（手机可用）落空，退化为桌面工具。

**对策**：
1. **V8 必须先做**，在写任何业务代码之前拿到真实数字。
2. 模型量化到 int8 / q4，控制单模型体积。
3. 实现 `lru.ts` 模型常驻管理，借鉴 hayamimi `--max-resident` 的思路。
4. 移动端默认使用**最小模型组合**（whisper-tiny.en + opus-mt tiny）。

**退路（按优先级）**：
- 退路 A：**分时复用**——VAD 断句后卸载 ASR，加载 MT 翻译，译完再切回。延迟上升约 0.5–1s，但内存峰值减半。
- 退路 B：手机上砍掉本地 LLM 摘要，只用 TextRank 抽取式（内存占用几乎为零）。
- 退路 C：手机上**只做「上传音频文件 → 转写 + 翻译 + 纪要」**，不做实时。功能弱化但依然可用、依然零成本。

### R2 🔴 Web Speech API 的隐私与可用性双重问题

**内容**：Chrome 的 `webkitSpeechRecognition` 在多数实现里会把音频送到 Google 服务器，与「音频不出设备」的隐私承诺冲突；且它只在 Chrome/Edge 可用，**iOS 上 Chrome 用的是 WebKit 内核，能力与 Safari 一致，行为不可控**。

**触发信号**：M1 实测发现 Web Speech 在 iOS 或 Firefox 上完全不可用。

**对策**：
1. UI 上**明确标注**「快速模式：识别在你的浏览器与识别服务之间进行」字样，绝不隐瞒。
2. 提供「隐私模式（全程本地）」开关。
3. 不把 Web Speech 当作唯一 L0 档——注册表里它只是**优先项**，探测失败立刻降级。

**退路**：把 Web Speech 从关键路径移除，L0 直接就是本地 WASM 模型。代价是首次打开要下载模型，体验变重。

### R3 🟡 Chrome 内置 Translator API 门槛过高

**内容**：要求 ≥22GB 可用磁盘、16GB 内存、4 核、4GB VRAM。大量普通笔记本和几乎所有手机都拿不到。

**触发信号**：`Translator.availability()` 返回 `'unavailable'` 的比例超预期。

**对策**：架构上它**只是四层里的一层**，缺失不影响主流程。`probe()` 拿不到就静默降到本地模型档。

**注意**：当 `availability()` 返回 `downloadable` / `downloading` 时，`Translator.create()` **必须由用户手势触发**，否则抛 `NotAllowedError`。所以 UI 上必须有一个「启用增强翻译」按钮 + `downloadprogress` 进度条，不能自动触发。

### R4 🟡 翻译质量不够（尤其数字）

**来源**：hayamimi 官方 Limitations 原文——"numeric values are not reliably preserved"。这是所有小模型的通病。

**影响**：纪要里的数字错了，比没有数字更糟（会误导）。

**对策**：
1. **数字不经翻译链路**：`factsExtractor.ts` 直接从英文原文用正则抽取数字/日期/百分比，附上中文参考译法，在纪要里以**对照表**形式呈现（原文 | 中文 | 出处）。
2. 数字抽取必须有单测（`tests/unit/factsExtractor.test.ts`）。
3. 摘要提示词里明确要求「只使用转写稿中出现的信息，不得编造」。

**退路**：若翻译质量整体不达标，调整为「英文原文完整保留 + 中文译文标注为参考」。

### R5 🟡 模型体积与首次加载体验（**M1 末实测更新**）

**内容**：ASR + MT 两个模型合起来 **159.6 MB**（whisper-tiny.en 42.4 MB + opus-mt-en-zh 117.2 MB），
而它们**随站点发布**（见 R15，为什么必须自托管），所以这 160 MB 是**每个新用户的首访下载量**，
也是托管的带宽消耗。手机流量下载体验差。

**对策**：
1. **分层加载**：先加载 ASR（用户能立刻看到效果），翻译模型后台预下载。
2. 明确显示剩余体积和网速估算（`approxBytes` 已改成实测字节数，不是估算）。
3. Cache Storage 持久化——**只下一次**，复访零流量。
4. **不做**「轻量模式」削减功能：模型已经压在 160 MB，再砍就只剩转写。
   真需要省流量时改用「最快启动」档（浏览器原生识别，零下载），但**国内这条路上
   Chrome 的原生识别同样不通**（音频要发往 Google 服务器），所以它只是桌面上的退路。

### R6 🟢 浏览器兼容性碎片化

**内容**：WebGPU / WebAssembly SIMD / AudioWorklet / CacheStorage 支持度不一。

**对策**：`lib/capability.ts` 统一探测，所有降级判断走它；**绝不写 `if (navigator.gpu)` 这种散落各处的判断**。

### R7 🟢 音频重采样与回声

**内容**：`getUserMedia` 拿到的采样率因设备而异（44.1k / 48k），必须重采样到 16kHz；外放时会有回声被重新拾取。

**对策**：AudioWorklet 做重采样；UI 提示「建议戴耳机」；可选 `echoCancellation: true` 约束。

## 二、产品与需求风险

### R8 🟡 需求方对「实时」的期望与现实不符

**内容**：真正的「同声传译」是毫秒级的。浏览器本地推理的实际延迟是 **1.5–2.5s**。用户可能期待「说完立刻出中文」。

**对策**：
1. 「动态调整」在 01 文档 N1 里把目标定成**首字 ≤1.5s、整句 ≤2.5s**，并让需求方确认。
2. UI 上用 partial（灰色草稿行）给出**即时反馈**，让用户感知到系统在动，缓解等待焦虑。
3. 借鉴 hayamimi 的 two-pass refine：先出粗糙的 live 结果（快），静音后再精修替换（准）。**用「快 + 越来越好」替代「一次性准确」。**

### R9 🟡 范围膨胀

**内容**：调研了 otoji 之后很容易想加「多人房间」「语音图编辑器」，这会把项目从「一个周末能做完的静态站」变成「需要服务器和账号的复杂系统」，直接破坏零费用约束。

**对策**：01 文档 §1.2 C 已明确列出**不做**的事。任何新增需求先问「会不会引入服务器成本」，会就拒绝或后置。

### R10 🟢 「免费」的可持续性

**内容**：GitHub Pages / Cloudflare Pages 免费额度对纯静态站几乎无限；但若将来加了任何服务端组件（房间、云同步），成本立刻出现。

**对策**：把「无服务端」当作架构铁律写进 04 文档。要加服务端功能，必须需求方**明确同意并承担费用**。

## 三、依赖与外部风险

### R11 🟡 上游 API/模型变更

**内容**：
- `Translator` API 仍在快速演进，旧版 `window.ai.translator` **已废弃**，未来说不准还会变。
- transformers.js / sherpa-onnx 的 API 也在动。
- Hugging Face CDN 上的模型文件可能被移除或改名。

**对策**：
1. 引擎层是**可替换实现**——API 变了只改 `engines/mt/chromeTranslatorMt.ts` 一个文件。
2. **模型已全部自托管**（放在自己的静态托管上），运行时不再依赖任何 CDN，见 R15。
   构建期的下载源 `hf-mirror.com` / `huggingface.co` 只影响「重新构建」，
   影响不到已经在跑的站点。
3. 锁死依赖版本，不自动升级。

### R12 🟢 许可证合规

**内容**：hayamimi 的 ja→en FuguMT 模型是 **CC BY-SA 4.0**（传染性）。各模型授权不同，仓库通常不含权重。

**对策**：
1. **只用 permissive 许可的模型**（Apache-2.0 / MIT）。
2. 上线前逐个核对模型卡上的 license，写进 `docs/` 记录。
3. 本项目自身用 MIT。

### R13 🔴 有 4 个文件超出 Cloudflare Pages 单文件上限（**M1 实测新增，M1 末扩充**）

**内容**：产物里有 **4 个**文件超过 Cloudflare Pages 的 **单文件上限 25 MiB = 26,214,400 字节**，
Cloudflare 会**直接拒绝整次部署**：

| 文件 | 字节 | MiB | 超 |
|---|---|---|---|
| `dist/assets/ort-wasm-simd-threaded.asyncify-CxOG5pUO.wasm` | 26,861,777 | 25.62 | +0.62 |
| `dist/models/Xenova/opus-mt-en-zh/onnx/decoder_model_merged_quantized.onnx` | 60,212,804 | 57.42 | **+32.42** |
| `dist/models/Xenova/opus-mt-en-zh/onnx/encoder_model_quantized.onnx` | 52,899,742 | 50.45 | **+25.45** |
| `dist/models/Xenova/whisper-tiny.en/onnx/decoder_model_merged_quantized.onnx` | 30,727,382 | 29.30 | +4.30 |

GitHub Pages 没有这个限制（站点 ≤1GB），所以「路线 A 双部署」的 Cloudflare 半边被卡死。
**这两类超限的性质完全不同**：

- **wasm 是能外置的** —— 它是 ONNX Runtime 的运行时，可以放到别处（如本仓库的 GitHub Release 资产）。
- **模型不能外置** —— 外置就等于回到「运行时从第三方 CDN 取权重」，而那正是这次改造要消灭的东西
  （见 R15，HF 实测 0/3 不通）。**削减模型文件数也没用**：q8 量化下每一片都超过 25 MiB。

ORT 同目录的其它 wasm 变体也**没有一个是能直接替换的**：

| 文件 | 字节 | 能否用 |
|---|---|---|
| `ort-wasm-simd-threaded.asyncify.wasm` | 26,861,777 | 实际被打进产物的就是这个，超限 |
| `ort-wasm-simd-threaded.jsep.wasm` | 28,352,885 | 更大 |
| `ort-wasm-simd-threaded.jspi.wasm` | 16,811,691 | 不同 ABI，JS 胶水不匹配 |
| `ort-wasm-simd-threaded.wasm` | 14,264,838 | 不同 ABI，JS 胶水不匹配 |

**对策（已落地）**：

1. **首选：主链接用 GitHub Pages**，Cloudflare 那半边先不部署 —— 功能完全一样，零成本承诺不受影响。
   `deploy-cloudflare.yml` 已改成**只支持手动触发**（`workflow_dispatch`），所以它不会在首次 push 时留下一条红记录。
2. **两个源站都要完整**时：把 wasm 上传为本仓库的 **GitHub Release 资产**（免费、无需付费账号），
   设置仓库变量 `VITE_ORT_WASM_BASE`，`vite.config.ts` 的 `ortWasmPolicy` 插件据此把超大 wasm 从产物里剔除，
   运行时由 `src/lib/ortEnv.ts` 交给 ORT 去外部取。
   ⚠️ 但这**只能解决 4 个里的 1 个**，3 个模型文件仍无解 —— 所以 Cloudflare 这条路在「模型自托管」之后
   实际上是关闭的，除非愿意把模型放回第三方 CDN。
   完整步骤见 [`09-本地运行与部署.md`](09-本地运行与部署.md) §9.4.3。
3. 增加机械闸门 `scripts/check-upload-size.mjs`（`pnpm lint:size`），在 CI 里**上传之前**就报出「哪个文件超了多少、怎么解决」，而不是把云厂商那句没信息量的报错丢给人。它现在把 wasm 与模型分成两段分别说明。
4. 两个开关**必须成对使用**：只删文件不设基址 → 本地模型加载失败；只设基址不删文件 → 上传被拒。

**残余风险**：外置 wasm 引入了两个新的外部主机（`github.com`、`objects.githubusercontent.com`），已同步加进 `scripts/check-zero-cost.mjs` 的允许清单，并注明「这是本项目自己的 Release 资产，不是第三方 API」。**不设 `VITE_ORT_WASM_BASE` 时这两个主机根本不会被请求**（默认走本地打包的 wasm）。

> 🟡 **实际采用的路线（M5 实测）**：站点最终发在 GitHub Pages ——
> <https://zkcwujiing.github.io/simulnote/>，`deploy-pages.yml` 的 build 与 deploy 两个 job 都跑绿。
> 该路线上**不存在单文件上限**，上面 4 个文件全部原样发布（实测 `HEAD` 返回 200
> 且 `Content-Length` 与本地字节数逐一相等）。**外置 wasm 的方案因此没有启用**
> （`VITE_ORT_WASM_BASE` 未设置），允许清单里的那两个 GitHub 主机也保持不被请求。
>
> ⚠️ 同时踩到一个**只能手动解决**的部署前置条件：`actions/configure-pages@v5`
> 即使用 `with: enablement: true` 也无法自动创建 Pages 站点，会报
> `Create Pages site failed. Error: Resource not accessible by integration`
> （创建站点要仓库管理员权限，`GITHUB_TOKEN` 永远拿不到）。**必须在
> Settings → Pages → Source 选一次 "GitHub Actions"**。特征很好认：
> Install / Fetch models / Build 全绿，**只有最后一步红**。详见
> [`10-上线清单.md`](10-上线清单.md) 第 3 步。

### R14 🟡 构建链在 Windows 上很脆（**M1 实测新增**）

**内容**：下面每一条都真实卡住过构建，且报错信息都指向错误的方向：

| 现象 | 真正原因 |
|---|---|
| `ERR_MODULE_NOT_FOUND: Cannot find package 'rollup'` | Windows 上用 junction 实现链接，Node 的 ESM 解析器不解析 junction。**必须**在 `pnpm-workspace.yaml` 写 `nodeLinker: hoisted`；写进 `.npmrc` 无效（当前 pnpm 不读） |
| `spawn EPERM` | 受限沙箱不允许子进程用管道 stdio，esbuild 起不来。与配置无关，换写法无用 |
| `remove C:\...\Temp\esbuild-xxxx: Access is denied` | 把 `TEMP`/`TMP` 指到项目内 `.tmp/` |
| `Cannot apply unknown utility class 'btn'` | Tailwind v4 的 `@apply` 只认工具类，自定义组件类必须写成纯 CSS |
| `ERR_PNPM_IGNORED_BUILDS` | 新版 pnpm 的 allowlist 在 `pnpm-workspace.yaml` 的 `allowBuilds`，键名和位置都与旧版不同 |

**对策**：
1. 全部写进 [`09-本地运行与部署.md`](09-本地运行与部署.md) §9.3，并在 `pnpm-workspace.yaml`、`vite.config.ts` 的注释里就地说明「为什么」。
2. CI（Ubuntu）上不会遇到第 1–3 条，说明这些是**本地 Windows 环境特有**的，不是代码问题 —— 出问题时先怀疑环境。
3. 提交前统一跑 `pnpm verify`（build + 零成本 + 体积闸门）。

### R15 🔴 模型来源被墙 → 改为自托管（**M1 末实测新增，架构级变更**）

**内容**：原本的设计是「浏览器直接从 Hugging Face CDN 下模型」。2026 年在这条网络线上实测：

| 目标 | 结果 |
|---|---|
| `https://huggingface.co` | **0/3 成功** —— DNS 被污染成 `59.188.250.54` / `185.45.6.57` 这类无效地址，TCP 443 不通 |
| `cdn-lfs.huggingface.co`（权重真正所在） | TCP 443 **不通** |
| `hf.co` | TCP 通，但真实请求 `…/resolve/main/config.json` **超时**（SNI 阻断） |
| `https://hf-mirror.com` | **10/10 成功**（国内镜像，可用） |
| 本机代理设置 | `ProxyEnable=0`、`ProxyServer` 空、`AutoConfigURL` 空、`HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 全空、hosts 无相关条目 —— **干净直连，没有代理** |
| `github.com` | 8–10/10 成功，**间歇性失败**（用户遇到的就是这个） |
| `github.io` / `pages.github.com` | 通（所以 GitHub Pages 托管本身没问题） |

后果不是「慢」，而是**站点能部署成功、打开却是砖**：卡在「正在加载模型」，
最后退化成「只转写、不翻译」—— 与原始需求（英译中）直接冲突。
**这与 R2/R3 不同：它是必然发生，不是概率问题。**

**对策（已全部落地）**：

1. **模型自托管**：构建期由 `scripts/fetch-models.mjs`（`pnpm fetch-models`）把 24 个文件 / 159.6 MB
   拉进 `public/models/`，随站点一起发布。`public/models/` 已进 `.gitignore`（仓库保持几百 KB，
   push 不会因跨境丢包反复失败），由 Actions 的 `fetch-models` 步骤补齐并用 `actions/cache/restore|save` 缓存。
2. **运行时零外部依赖**：`src/lib/modelSource.ts` 的 `configureModelSource(env)` 设
   `allowLocalModels=true` / **`allowRemoteModels=false`** / `useBrowserCache=true`，
   `localModelPath = import.meta.env.BASE_URL + 'models/'`（**必须带 base 前缀**，否则 GitHub Pages 子路径 404）。
   `allowRemoteModels=false` 是**护栏**：清单少文件时立刻报错，而不是悄悄回落到 HF 再在用户那儿超时。
3. **零成本白名单同步收紧**：`scripts/check-zero-cost.mjs` 的 `ALLOWED_HOSTS` 已**删掉**
   `huggingface.co` / `hf.co` / `.huggingface.co` / `.hf.co`，现在只剩 GitHub 系（且只服务于可选的 ORT wasm 外置）。
   `hf-mirror.com` **不进白名单** —— 它只是构建期的下载源，可用性不能押在第三方镜像的善意上。
4. **`pnpm build` 的新第一步**：`node scripts/fetch-models.mjs --check`（离线体检 24/24），
   拦住「忘了拉模型就构建」。pnpm 7+ 不自动跑 pre/post 脚本，所以必须显式写在 build 里。
5. 模型清单**砍到只剩两个**：`Xenova/whisper-tiny.en`（42 MB，MIT）与 `Xenova/opus-mt-en-zh`（117 MB，Apache-2.0）。
   原来候选里的 nllb-600M / m2m100-418M / whisper-base 都去掉了 —— 自托管下每多一个候选就是多一份必须发的体积。

**残余风险（已升级为要盯的指标）**：GitHub Pages 带宽 100 GB/月（软限制）÷ 每次完整首访 186 MB ≈ **550 人次/月**。
链接被大量转发会先撞到这条。退路：把 `models/` 挪到 Cloudflare R2（出网流量免费），
**只改 `src/lib/modelSource.ts` 一处**，仍然零成本。

**踩过的坑（写进代码注释了）**：`scripts/fetch-models.mjs` 最初用 `HEAD` 的 `Content-Length` 做跳过/校验，
但 hf-mirror 对 `Xenova/whisper-tiny.en/tokenizer_config.json` 返回 `200 + content-length: 20`（真实 835 字节），
好文件被当成「长度不符」删掉。**文件大小一律以 tree API（`/api/models/<id>/tree/main?recursive=true`）为准。**

### R16 🔴 ONNX Runtime 的运行时被悄悄送去第三方 CDN（**真机实测才暴露，已处置**）

**内容**：真机（手机）上跑探针 ⑤「本地模型实测」，V2（Whisper）与 V4（opus-mt）**双双失败**，
报错一模一样，且都在 `pipeline()` 里：

```
TypeError: Load failed
```

所有计时字段都是 `—`（连下载都没开始）。**这个报错极具误导性** ——
它看起来像「模型文件加载失败」，于是第一反应会去查模型路径、跨域、文件是否存在。

**实测排除**：
- `public/models/` 下 **24/24** 个文件线上 `HEAD` 全部 200；
- `transformers.web.js` 里根本没有 `Load failed` 这个字符串 —— 它来自浏览器网络层；
- 本机（桌面）访问 jsDelivr 的根域、`fastly.` 子域、以及那个**精确到 dev 版本号**的文件 URL，全部 200。

**真正的根因**：transformers.js 打包进产物的代码（`dist/assets/transformers-*.js`）里有：

```js
if (... && Ye.versions?.web && !Ye.wasm.wasmPaths) {
  const t = `https://<第三方静态资源 CDN>/onnxruntime-web@${Ye.versions.web}/dist/`;
  let r = ".asyncify";
  fe.IS_SAFARI_BELOW_26 && !fe.IS_WEBGPU_AVAILABLE && (r = "");
  Ye.wasm.wasmPaths = { mjs: `${t}ort-wasm-simd-threaded${r}.mjs`,
                        wasm: `${t}ort-wasm-simd-threaded${r}.wasm` };
}
```

**只要 `env.backends.onnx.wasm.wasmPaths` 为空，ORT 的 JS 胶水和 26.8 MB 的 wasm 就都从那个 CDN 取。**
而当时的情况是：`src/lib/ortEnv.ts` 的 `configureOrtWasm` 第一行就是
`const base = ortWasmBase(); if (!base) return;`（只在设了 `VITE_ORT_WASM_BASE` 时才生效，
而本项目从未设），并且 **`src/probe/probes.ts` 压根没调用它**。
于是站点里那个 Vite 顺带产出的 26.8 MB wasm 是**死重，从未被使用**。

**为什么护栏没拦住**：`scripts/check-zero-cost.mjs` 当时只扫 `src/`、`public/`、两个 HTML 入口，
**既不扫 `node_modules` 也不扫 `dist`**。那个 CDN 字面量在依赖包里，构建之后才进产物。

**对策（已全部落地，见提交 `3d40184`）**：

1. **`src/lib/ortEnv.ts` 的 `configureOrtWasm` 改为无条件设置 `wasmPaths`**，
   默认指向本站 `` `${siteBase()}ort/` ``，**不再有「没设变量就回落到 CDN」这条路径**。
   同时按 transformers.js 自己的规则选变体：Safari 主版本 < 26 且无 WebGPU → 非 asyncify 那份，其余 → asyncify。
2. **`vite.config.ts` 新增 `ortRuntime()` 插件**：构建时从 `node_modules/onnxruntime-web/dist/`
   拷**两对**运行时（asyncify 26.8 MB + 普通 14.3 MB）到 `dist/ort/`。同时 `ortWasmPolicy()`
   改为**无条件剔除**产物里 >12 MiB 的 `.wasm`（那个死重）。
3. **探针把「运行时到底从哪儿取」写进报告**：新增 `describeWasmPaths()`，V2/V4 的 details 各加一行
   `ORT 运行时来源`。**上次翻车的直接教训就是这一行不存在**，导致把 CDN 问题误判成模型问题。
4. **护栏补三个盲区**：`NAMED_BAD_HOSTS` 新增 jsDelivr / unpkg / cdnjs / skypack / esm.sh / esm.run / cdn.tailwindcss.com；
   新增**产物扫描**（`dist/ort/` 四个文件必须在位；`dist/assets/*.wasm` 不得 >12 MiB；
   库内 CDN 字面量只记录不报错，因为它删不掉、靠覆写中和）；
   新增**调用点护栏**（凡 `src/` 下引用 `@huggingface/transformers` 的文件必须同时调用 `configureOrtWasm()`）。
5. 体积代价：`dist` 从 186 MB 变 **199.96 MB**（+41 MB 两对运行时，−26.8 MB 死重），换的是
   「任何一台设备都不会因为 CDN 连不上而变成砖」。

**残余风险（待真机复测确认）**：GitHub Pages 给 `.mjs` 下发的 `Content-Type` 若不是 JS MIME，
动态 `import()` 仍会失败 —— 部署后必须实测该响应头。另外 `SharedArrayBuffer=false` 下
ORT 胶水函数体内的 `var SharedArrayBuffer = globalThis.SharedArrayBuffer ?? (new WebAssembly.Memory({shared:!0})).buffer.constructor;`
是否抛异常，仍然**没有实测到**。

> **上述两条已实测排除（2026/10/5）**：`.mjs` 线上 `200 · text/javascript; charset=utf-8 · 53,057 字节`；
> 且修复后 V2（Whisper）在 iPhone Safari 上**跑通，RTF = 0.217**，说明 `SharedArrayBuffer=false`
> 下 ORT 也能正常初始化。**COOP/COEP 由「前提」降级为「优化项」。**



### R17 🔴 GitHub Pages 给 `.onnx` 加 gzip + 单次长响应太大 → 大模型在手机上必然断（**真机实测定位，已处置**）

**内容**：R16 修好后，V2（Whisper，单文件最大 29.3 MB）在 iPhone Safari 上通过，
但 V4（`Xenova/opus-mt-en-zh`，编码器 50.45 MB / 解码器 57.42 MB）**仍然失败**，
报错还是那句 `TypeError: Load failed`。而两份报告里「ORT 运行时来源」一模一样 ——
所以这**不是** R16 的残留，是另一个问题。

**关键实测数据（`scripts/` 之外用 curl 直接探线上文件）**：

| 请求方式 | 状态 | `Content-Length` | `Content-Encoding` | `Content-Range` |
|---|---|---|---|---|
| 默认（带 `Accept-Encoding: gzip, deflate, br`） | `200 OK` | **37,142,901** | **`gzip`** | 无 |
| `Accept-Encoding: identity` | `200 OK` | 52,899,742 | 无 | 无 |
| `Range: bytes=0-1023` | **`206 Partial Content`** | 1,024 | **无** | **`bytes 0-1023/52899742`** |
| `HEAD`（`curl -I`） | `200 OK` | 52,899,742 | 无 | 无 |

**两个决定性事实**：

1. **GitHub Pages 会对 `.onnx` 做 gzip**：37,142,901 / 52,899,742 ≈ **0.702**。
   所以探针日志里那句「encoder 35.4MB」是**压缩后**的 `Content-Length`，不是文件大小 ——
   浏览器要在**一次长连接**里收完 37 MB 压缩流、再解压成 50 MB。
   而 `Content-Length` 报的是压缩后长度，**前端连「还剩多少」都算不出来**。
   裸取探测（绕开 transformers 和 ORT，直接 `fetch`）**只收到 4.5 MB 就断**。
2. **一旦请求带 `Range`，服务端就不压缩了**，返回的是「未压缩文件的字节区间」，
   而且 `Content-Range` 里带着**真实**总长度 52,899,742。→ **分块下载这条路是通的。**

**为什么必须连 transformers.js 的缓存一起换掉**：它读缓存只做
`caches.match(request)`，命中就**直接返回、不校验长度**。一次断线留下的**半截文件会被永久缓存**，
之后每次启动都命中那个坏条目、连网络都不发 —— 症状就是「清了缓存就好、不清就永远坏」。
**这个坑会让任何网络层的修复看起来无效。**

**对策（见 `src/lib/modelSource.ts`）**：

1. **`env.useBrowserCache = false`**，缓存改由 `cachedModelFetch` 自管（`simulnote-models-v1`）：
   写进去的一定是校验过总长度的完整文件，读出来长度对不上就**当场删掉重下**。
   同时顺手 `caches.delete('transformers-cache')` 清掉旧版本留下的不可信条目。
2. **`.onnx` 一律走 `Range` 分块**：每块 2 MB，拼成 Blob 后伪装成一个正常 `200` 响应交给
   transformers.js。任何一块断了**只重下那一块**；连续失败就把块体积**减半**（下限 512 KB）。
3. **长度必须核对**：`Content-Range` 给出的总长度和最终拼出的字节数不一致就报错，
   绝不把半截数据写进缓存 —— 这是与 R16 那次「静默失败」最大的区别。
4. **诊断可见**：抓取日志每条现在多一行 `↳` 说明（`本地缓存 xx MB` / `分块下载 x / y MB` /
   `分块中断，块大小降到 …`），下一次真机报告能直接看出走的是哪条路。

**残余风险**：分块下载的请求数变多（编码器 26 次、解码器 29 次），首次访问总时长可能变长；
`Range` 在非 GitHub Pages 的静态托管上行为需重测（Cloudflare Pages 走的是另一套）。


### R18 🔴 源站吞吐才是首访慢的真凶：GitHub Pages 只有 0.06 MB/s（**实测定位，已处置**）

**现象**：R17 修好后 V4 在小米平板上**通过了**，但「加载 729 秒」——首访要 12 分钟，
对一个演示型产品等于不可用。

**定位过程（先证伪三个猜测）**
1. ~~模型文件缺件~~ —— `scripts/fetch-models.mjs` 的 24 个文件已逐条对照，一条不缺。
2. ~~换模型 id~~ —— 这个方向是错的，V2 与 V4 的 ORT 来源完全相同，问题不在模型。
3. ~~分块请求数太多拖慢~~ —— 实测块 2 MB / 4 MB / 8 MB / 16 MB 分别是 0.14 / 0.12 /
   0.10 / 0.08 MB/s，**块越大反而越慢**，请求数不是瓶颈。
4. ~~并发不够~~ —— 4 块并发 93.5 秒，串行 86.1 秒，**毫无加速**；8 块并发直接 ECONNRESET。
   说明是**总量限速**，不是每连接限速。

**决定性实测**（本机家宽，同一个 opus 编码器、同样连取 4 个 8 MB 区间）

| 源 | 第 1 次 | 第 2 次 | 第 3 次 | 第 4 次 |
|---|---|---|---|---|
| hf-mirror.com | 1.23 MB/s | 失败 | 0.44 MB/s | 0.70 MB/s |
| 自建 GitHub Pages | 0.06 MB/s | 0.06 MB/s | 0.05 MB/s | 0.06 MB/s |

同一批对照里：jsDelivr npm 2.43 MB/s、npmmirror 7.15 MB/s、npmjs 官方 2.35 MB/s、
HuggingFace **连不上**（与文件头注释一致）。

**结论**：慢的不是模型、不是分块策略、不是并发，是 **GitHub Pages 从国内取大文件约 0.06 MB/s**。
按 0.06 MB/s 算，108 MB 的翻译模型要 **30 分钟**；按 0.15 MB/s（平板实测反推）算也要 12 分钟
—— 与 729 秒完全吻合。

**对策：双源自动测速（`src/lib/modelSource.ts`）**
1. 候选两个源：**自建**（`${base}models/`，永远是兜底）与 **hf-mirror.com**。
2. 每个源先取 256 KB 测速（20 秒超时），**谁快用谁**；结论记进 `localStorage`，
   1 小时内不重复测（不白花 512 KB 流量）。
3. transformers.js 只会朝自建要文件，但所有 `/models/` 请求都被 `instrumentFetch` 截住，
   地址改写到选中的源上。
4. **缓存键永远用自建的规范地址** —— 换源之后之前下好的文件照样命中，不会白下第二遍。
5. 主源失败就自动换另一个源重试一次；两个都失败才报错（宁可慢，不能不能用）。
6. 探针页新增「模型来源（自动测速）」一行，直接印出 `测速 自建 0.06 MB/s · hf-mirror 1.64 MB/s → 选 hf-mirror`。

**顺带修掉的两个缺陷**
- `responseFromBlob` 原来**不设 `content-length`**，导致 transformers.js 的进度回调算不出百分比，
  界面上整段下载显示成「卡住不动」，报告里的「下载耗时」也会变成 0。现已补上。
- `rangeDownload` 原来**块一经缩小就不再涨回**。实测 hf-mirror 取 53 MB 时出现 32 次重试，
  块停在 512 KB 会让剩下的文件多发几十个请求、总时长被拖到 305 秒（平均仅 0.165 MB/s）。
  现改为**连续成功 4 块就翻倍涨回**，上限仍是 2 MB。

**残余风险**
- 镜像可能被墙、限速或停服 —— 自建兜底，最坏情况退化成今天的 0.06 MB/s，**不会不能用**。
- 256 KB 的测速量的是**突发速度**，与持续速度不完全一致（实测首次 1.23 MB/s、后续 0.44–0.70 MB/s）。
  量级上仍足以区分 0.06 与 0.7 这两个源，所以够用；但如果将来两个源都接近，需要把探针放大。
- hf-mirror 是社区镜像，**没有 SLA**。这是本次为了可用性付出的代价，已由用户明确选型。


## 四、风险处置优先级（如果只能做三件事）

1. **立刻做 V8（手机内存探针）** —— 它决定项目形态，不确定它就不知道该写什么代码。
2. **数字抽取独立于翻译链路** —— 这是最容易被忽视、代价最高的缺陷。
3. **守住「无服务端」铁律** —— 一旦破坏，零费用承诺立刻失效。
