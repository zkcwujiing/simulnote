# V0 · 设备画像（P0 探针）

- **测试设备**：华为 P60 Pro（机型代号 `MNA-AL00`），Android 12，屏幕 `400×886` CSS px / DPR 3.05（≈1220×2702 物理像素）
- **测试浏览器**：**微信内置浏览器**（`MicroMessenger/8.0.78.3180`，内核 XWEB/1500145，UA 里报 `Chrome/150.0.7871.189 Mobile Safari/537.36`，`wv` 外壳）
- **测试时间**：2026-（首次真机测试）
- **方法**：手机打开 <https://zkcwujiing.github.io/simulnote/probe.html> → ① 「跑全部零下载项」（**不下载任何模型**，纯能力探测）
- **判定**：**及格但有隐患**（探针自己给的判定）

> ⚠️ 这次测的是**微信内置浏览器**，不是系统 Chrome。这一点很关键 ——
> 用户要「发链接给朋友」，朋友点开后默认就在微信里，所以**微信 webview 才是主战场**，
> 系统浏览器反而是备选。下面所有结论都只对微信 webview 成立。

## 结论

**及格但有隐患。** 好消息比预期多，坏消息集中在一处。

### 好的部分（实测通过，可以依赖）

1. **`AudioContext` 能直接开在 16000 Hz** —— 这一条消掉了一大块风险。
   `src/lib/audio/capture.ts` 的重采样路径在手机上可以走「原生 16k」这条快路，
   不必依赖 AudioWorklet 里自己写重采样。`public/pcm-worklet.js` 仍然要保留，但它是保底，不是主路。
2. **AudioWorklet 和 ScriptProcessor 都在** —— 采集层两档降级都有实物，
   `src/lib/audio/capture.ts` 的双路径设计在这台机器上是可用的。
3. **Cache Storage 能真写真读（4 MB 往返）**，配额 10 GB —— 160 MB 模型缓存得下，
   复访不用重新下载。这是「自托管模型」方案能在手机上成立的前提，**现在它被证实了**。
4. **WebGPU 存在，适配器是 `qualcomm`**，`maxBufferSize` 1024 MB —— 比预期好。
   手机端不必一开始就放弃 WebGPU 后端。
5. **WASM SIMD = true** —— q8 量化模型能吃到 SIMD 加速。
6. **8 个逻辑核心** —— 如果将来能拿到多线程，收益的硬件基础是有的。

### 坏的部分（需要对应处置）

1. 🔴 **`crossOriginIsolated = false` / `SharedArrayBuffer = false` → 没有 WASM 多线程，探针判「速度约一半」。**
   根因：GitHub Pages **不能下发自定义响应头**，拿不到 `COOP: same-origin` + `COEP: require-corp`。
   - 对 ORT 的直接后果**还没测到**：我们发的是 `ort-wasm-simd-threaded.asyncify.wasm`（线程版）。
     该构建的 JS 胶水里有这一行：
     `var SharedArrayBuffer = globalThis.SharedArrayBuffer ?? (new WebAssembly.Memory({initial:0,maximum:0,shared:!0})).buffer.constructor;`
     在非 COI 页面里 `globalThis.SharedArrayBuffer` 是 `undefined`，于是会去构造一块 **shared** 的
     `WebAssembly.Memory` —— 这一步在部分内核上会抛异常，**那样 ORT 会整个初始化失败，模型根本跑不起来**。
     另有 `if(!globalThis.SharedArrayBuffer)return 6;` 说明线程创建路径是明确会失败的（但单线程路径不依赖它）。
     **这一条是本次最大的未知，必须实测。**
   - 已知的绕过手段（尚未实施）：用一个 **Service Worker 给同源响应补上 COOP/COEP**（社区里叫 coi-serviceworker）。
     我们是自托管、运行时零外部依赖，`require-corp` 不会挡掉任何跨源资源，**理论上条件齐全**；
     但微信 webview 支不支持这个组合是未知数。
2. 🟡 **`浏览器原生识别：没有`** —— 手机端**没有** Web Speech 兜底。
   原来「L0 用浏览器原生 API」这一档在手机上直接作废，`asr-webSpeech` 在这台设备上必然走不通。
   **降级链的第一档必须直接跳到本地 Whisper**（`docs/03` 的四层降级链要按这个新事实改）。
3. 🟡 **JS 堆上限 2994.54 MB 是「浏览器愿意给的数」，不是「系统真的会给」。**
   `deviceMemory=8` 同样是被钳过的粗略值。真实 OOM 阈值只能靠 V8 内存压力测试测出来，**现在还没测**。
4. 🟡 **微信 webview 的额外不确定性**：`wv` 外壳、10 GB 配额是「配额」，微信自己还有缓存清理策略；
   42 MB + 117 MB 的模型下载在微信里会不会被限速/中断，**没测**。

## 对架构的影响

1. **`docs/03` 的四层降级链在手机上要改成三档**：`asr-webSpeech` 这一档在移动端直接跳过（实测无此能力），
   保留它只对桌面 Chrome/Edge 有意义。
2. **「手机能不能跑」这件事完全押在本地 Whisper 上**，因此下面这条数据从「重要」升级为「**唯一决定性**」：
   > 在这台手机上，`Xenova/whisper-tiny.en` q8 的 **RTF（推理耗时 ÷ 音频时长）** 是多少。
   - 如果 RTF ≤ 0.6 → 单线程也能用，**COI/多线程从「必需」降级为「优化」**。
   - 如果 RTF 在 0.6–1.0 → 勉强能用，但必须上 COI Service Worker 换多线程，否则长会话语音会越积越多。
   - 如果 ORT 直接初始化失败 → **COI Service Worker 从「优化」变成「唯一出路」**，而且必须先验证微信 webview 支持它。
3. **采集层可以简化**：既然实测能直接开 16 kHz 的 AudioContext，主路径就该优先走它，
   AudioWorklet 重采样只作为降级（这条要写进 `docs/04`）。
4. **分享体验要加一条**：朋友在微信里打开是最可能的路径，UI 需要一个「建议用系统浏览器打开」的提示
   （微信右上角 →「在浏览器打开」），并且在微信里要能优雅降级而不是白屏。

## 下一步（按优先级）

1. **⑤ 本地模型实测**（探针页），Whisper 单跑、合成音频 10 秒、WASM q8 —— 拿到 RTF 和「到底能不能初始化」。
2. 同一节换 **WebGPU fp32** 再跑一次 —— 有 `qualcomm` 适配器，值得试。
3. **② V8 内存压力**（**放最后跑**，它可能把标签页弄崩，这是故意的）。
4. 换**系统浏览器**（Chrome / 华为浏览器）再跑一遍 P0，和微信内的数字做对照。
