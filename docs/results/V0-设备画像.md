# V0 · 设备画像（P0 探针）—— 同一台手机上的三种浏览器

- **测试设备**：华为 P60 Pro（机型代号 `MNA-AL00`）
- **测试浏览器**：① 微信内置浏览器 ② 华为浏览器 ③ Chrome（**同一台机器，三次独立测试**）
- **测试时间**：2026-（首次真机测试，三次间隔约 3～17 分钟）
- **方法**：手机打开 <https://zkcwujiing.github.io/simulnote/probe.html> → ① 「跑全部零下载项」（**不下载任何模型**，纯能力探测）
- **判定**：三者**全部**「及格但有隐患」

> 这份报告最初的版本只测了微信内置浏览器。补测系统浏览器之后，结论发生了一个**方向性的变化**：
> **缺多线程 WASM 不是微信的锅，也不是任何一个浏览器的锅 —— 是 GitHub Pages 的锅。**
> 三个内核（XWEB / 华为 / Chromium 150）在这项上给出的答案一模一样。详见下面「结论」第 1 条。

## 结论

### 1. 🔴 决定性的一项，三个浏览器答案完全一样 —— 所以这不是浏览器问题

`crossOriginIsolated` / `SharedArrayBuffer` / WASM 多线程在**三个内核上全是 false**。

这说明根因不在客户端，而在服务端：**GitHub Pages 不允许下发自定义响应头**，拿不到
`Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`。
换浏览器、换手机、换系统都改变不了这一条。

**对 ORT 的直接后果仍然没测到。** 我们发的是 `ort-wasm-simd-threaded.asyncify.wasm`（线程版），
它的 JS 胶水里有一行：

```js
var SharedArrayBuffer = globalThis.SharedArrayBuffer ??
  (new WebAssembly.Memory({initial:0, maximum:0, shared:!0})).buffer.constructor;
```

非 COI 页面上 `globalThis.SharedArrayBuffer` 是 `undefined`，于是会真的去构造一块 **shared** 的
`WebAssembly.Memory`。这一步在部分内核上会抛异常 —— **那样 ORT 会在初始化阶段整个失败，模型根本加载不了**。
另有 `if(!globalThis.SharedArrayBuffer)return 6;` 说明线程创建路径是明确会失败的（但单线程路径不依赖它）。

好消息是：`numThreads` 在整份胶水里**只出现一次读取、没有任何地方赋值**，默认走单线程路径 ——
那是被支持的正常配置。所以推测偏向「大概率能跑，只是慢」，**但这是推测**。

绕过手段（**尚未实施**）：用 Service Worker 给同源响应补上 COOP/COEP（社区叫 coi-serviceworker）。
我们是自托管、运行时零外部依赖，`require-corp` 不会挡掉任何资源，**理论上条件齐全**；
但微信 webview 支不支持这个组合是未知数 —— 而三个浏览器里最需要它活下来的恰恰是微信。

### 2. 🟢 三者一致通过的部分（可以放心依赖）

- **`AudioContext` 能直接开在 16000 Hz**（三个都是），`能强制 16kHz = true` —— 采集层可以走原生 16k 快路。
- **AudioWorklet + ScriptProcessor 都在** —— 采集层两档降级都有实物。
- **Cache Storage 真写真读 4 MB 成功**（三处都成功）—— 自托管模型「下一次不用重下」的前提被证实。
- **WASM SIMD = true** —— q8 量化模型吃得到 SIMD。
- **WebGPU 存在且三者参数相同**（`qualcomm`，`maxBufferSize` 1024 MB）—— 手机端不必一开始就放弃 WebGPU。
- **8 个逻辑核心** —— 将来若拿到多线程，硬件基础是有的。

### 3. 🟡 三者之间**唯一**有意义的差别：JS 堆上限

| | 微信 / Chrome | 华为浏览器 |
|---|---|---|
| JS 堆上限 | 2994.54 MB | **1077.65 MB** |

华为浏览器的内核是 **Chromium 132**，比另外两个（150）低 18 个大版本；堆上限低到 1/3，
说明它跑在一个更保守的配置里。

**但要克制，别把它当成致命伤**：ORT 用的是 **wasm 线性内存**，V8 不计入 JS 堆上限。
所以 1077 MB 的 JS 堆**未必**是跑模型的瓶颈 —— 它更像是「页面上 JS 对象太多时会先崩」的信号。
真正确认这一点要靠 V8 内存压力探针，而不是靠这个数字。

### 4. 🟡 `浏览器原生识别：没有` —— 三个都没有

`asr-webSpeech` 这一档在移动端**彻底作废**，保留它只对桌面 Chrome/Edge 有意义。
`docs/03` 的四层降级链在手机上要改成三档。

## 该用哪个浏览器

**开发与测量用 ③ Chrome**；**架构按 ① 微信 webview 设计**。

- **用 Chrome 测**：真实 Chromium、内核版本最高（150）、JS 堆上限 2994 MB、没有 webview 外壳的额外限制。
  量 RTF、量内存，用最干净的那个环境，数字才有可比性。
- **按微信设计**：用户要「发链接给朋友」，**朋友点开后默认就在微信里**。微信那档如果不能优雅降级，
  这个项目对朋友就是不可用的。华为浏览器那 1077 MB 的堆上限也要当作警钟 —— 它是三者中最紧的约束。

**一句话**：拿 Chrome 当尺子，拿微信当靶子。

## 对架构的影响

1. **`docs/03` 的四层降级链在手机上改成三档**：`asr-webSpeech` 在移动端直接跳过（三次实测都没有）。
2. **「手机能不能跑」完全押在本地 Whisper 上**，因此这条数据从「重要」升级为「**唯一决定性**」：
   > 在这台手机上，`Xenova/whisper-tiny.en` q8 的 **RTF（推理耗时 ÷ 音频时长）** 是多少。
   - RTF ≤ 0.6 → 单线程也能用，**COI/多线程从「必需」降级为「优化」**。
   - RTF 在 0.6–1.0 → 勉强能用，但必须上 coi-serviceworker 换多线程，否则长会话语音会越积越多。
   - **ORT 初始化直接失败 → coi-serviceworker 从「优化」变成「唯一出路」**，且必须先验证微信 webview 支持它。
3. **采集层简化**：实测能直接开 16 kHz，主路径优先走它，AudioWorklet 重采样只作降级（写进 `docs/04`）。
4. **分享体验加一条**：微信里打开是最可能的路径，UI 需要「建议用系统浏览器打开」的提示
   （微信右上角 →「在浏览器打开」），并且要能优雅降级而不是白屏。
5. **COI 这条路要重新评估优先级**：既然它在三个浏览器上一致缺失、且根因在 GitHub Pages 而非客户端，
   就不能指望「换个浏览器就好了」——要么上 coi-serviceworker，要么接受单线程，要么换托管（Cloudflare 那半边已关）。

## 下一步（按优先级）

1. **⑤ 本地模型实测**（探针页）：Whisper 单跑、合成音频 10 秒、WASM q8 —— **用 Chrome 跑**
   —— 一次同时回答「ORT 到底能不能初始化」和「RTF 是多少」。
2. 同一节换 **WebGPU fp32** 再跑一次（有 `qualcomm` 适配器，值得试）。
3. 拿 ① 微信 webview **重跑同一项**，看它和 Chrome 差多少 —— 这才是朋友会遇到的数字。
4. **② V8 内存压力**（**放最后跑**，它可能把标签页弄崩，这是故意的）。
5. 华为浏览器那 1077 MB 堆上限，值得单独跑一次内存压力，确认它是不是真的更早崩。
