**已经用数据确认的三件事**（不再是推断）：

- **多线程 WASM 在五个浏览器上全部不可用** —— `SharedArrayBuffer` 与 `crossOriginIsolated` 全是 `false`，
  根因是 **GitHub Pages 不能下发自定义响应头**，不是任何一个浏览器的问题。
- **WebGPU 两台设备都有**（高通 `qualcomm` / 苹果 `apple`），但**都还没用它跑过模型**。
- **`AudioContext` 能直接开在 16000 Hz、Cache Storage 能真写真读** —— 两台、五个浏览器全部通过。

其余结论现在仍然只是推断，不是数据：

- 手机跑本地 Whisper 到底有多快（**RTF**）、要多少内存 ← **现在最缺的就是这个**
- WebGPU 能不能真的用来跑 Whisper（有适配器 ≠ 跑得动）
- 本地 opus-mt 类模型的翻译质量人读不读得懂
- 手机标签页实际能要到多少内存（OOM 阈值）
- 抽取式摘要挑出来的句子是不是真的重要

## 怎么跑

探针页和主应用是同一份构建，两个入口：

| 场景 | 打开哪个地址 |
|---|---|
| 本机（桌面） | `pnpm dev` 然后开 `http://localhost:5173/probe.html` |
| 手机 | 部署上线后，在分享链接后面加 `/probe.html` |

⚠️ 手机上跑「内存压力测试」会故意把内存用到接近极限，**有可能导致标签页被系统杀掉**。
这是故意的 —— 我们要的就是那个阈值。跑之前先存好别的页面。

跑完点「**复制报告**」，会得到一整份 Markdown。把它按下面命名存成文件即可。

## 文件命名

| 文件 | 对应探针 | 谁必须跑 |
|---|---|---|
| `V0-<设备>.md` | 设备画像 P0（**零下载**，先跑这个） | 每台目标设备各一份；**同一设备上每个不同内核**各跑一遍（Android：微信 / 华为 / Chrome 是三个内核；iOS：Chrome 和 Safari 都是 WebKit，跑一个即可） |
| `V1.md` | sherpa-onnx WASM 流式英文 ASR | 桌面 + 手机 |
| `V2.md` | transformers.js Whisper 的实时性 | 桌面 + 手机（**最关键的之一**） |
| `V3.md` | Chrome 内置 Translator API | 桌面 Chrome 138+ |
| `V4.md` | opus-mt / bergamot 的 WASM 质量与速度 | 桌面 + 手机 |
| `V5.md` | WebLLM 跑 Qwen2.5-1.5B 做摘要 | 桌面（可选） |
| `V6.md` | 纯 JS TextRank 抽取式摘要的兜底质量（**已由 `pnpm bench:summary` 自动化，不能手改**；2026/10/7 语料重做后 precision@5 100%、决策/待办 4/4） | 任意设备（秒出） |
| `V7.md` | Silero VAD 的 CPU 占用 | 桌面 + 手机 |
| `V8.md` | **移动端真实能力边界（内存 / 配额 / OOM 阈值）** | **每台目标手机都要单独跑** |

> 探针页目前覆盖的是 V2 / V3 / V4 / V6 / V8 以及基础设施画像。
> V1（sherpa-onnx）、V5（WebLLM）、V7（Silero VAD）需要额外引入依赖，
> 等 V2/V4 的结果出来、确认走哪条路之后再补 —— 先用最小代价回答「值不值得做」。

## 一条自我约束

报告里**不要写「应该可以」**。要么有数字，要么写「没测到」。
M0 的全部价值就在于把「应该可以」换成数字 —— 一旦允许推测混进来，
这些文档就会和之前那些「看起来很有道理」的假设一样，失去作用。
