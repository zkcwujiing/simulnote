## 三、新暴露的问题：**首访加载 729 秒（12 分钟）**

这是本次报告里唯一需要立刻处理的事。

| | 数值 | 说明 |
|---|---|---|
| V2 下载 + 加载 | 356,936 ms | 其中下载只有 37,436 ms → **319 秒不在下载上** |
| V4 下载 + 加载 | 729,381 ms | 108 MB 模型；按 0.8 MB/s 算下载应约 135 秒 |

**两个疑点：**

1. **下载之外的那几百秒是什么？** V2 有 319 秒、V4 有约 594 秒无法用「下载」解释。
   可能是：ORT 会话创建（把 50 MB 计算图编译成 wasm 可执行形式）、
   或分块下载的**请求数开销**（108 MB ÷ 2 MB = 54 次请求，每次至少一个 RTT）。
2. **探针的「下载体积」和「其中下载」现在不可信了。** `25d908f` 之后，
   我们交给 transformers.js 的是一个已经下载好的 Blob，
   它的进度回调**看不到真实下载过程**，所以这两栏数字失去了意义。

**下一步的测量方案**（已在 `.tmp/chunk-bench.mjs` 里写好对照方法）：
对同一个 8 MB 窗口，分别用 2 / 4 / 8 / 16 MB 的块去取，比较总耗时与吞吐。
如果块越大越快，说明瓶颈是**请求数**，那就把块调大；
如果块大小无关，说明瓶颈是**单连接带宽**，那就只能靠预取和进度提示来改善体验。

## 四、对项目的影响

1. **M0 的核心未知已经解决**：转写与翻译这两条最重的链路，
   分别在 iPhone Safari 与小米平板上跑通，RTF 0.259 / 吞吐 3.1 句/秒，余量充足。
2. **M0 还没跑的是 V1（sherpa-onnx）、V5（WebLLM）、V7（Silero VAD）、V8（内存压力）。**
   其中 **V8 仍然是「最该补的一个数字」** —— 它决定长时间会议会不会被杀标签页。
3. **首访体验是现在最大的产品风险**，不是模型能力。12 分钟白屏无人能忍，
   必须做到「分段可见进度 + 可中断可续传 + 明确告知还要多久」。
4. **译文质量要求把「数字抽取」提到核心地位**（原本排在 M3）。
