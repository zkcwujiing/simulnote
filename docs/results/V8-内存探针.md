## 二、这份报告能说明什么

**能说明的**：在这台设备上，`whisper-tiny.en` 与 `opus-mt-en-zh` **两条 pipeline 可以同时驻留**，
而且驻留之后还能再拿到至少 2 GB —— 「边听边译」在内存上没有任何问题。

**不能说明的（重要）**：

1. **`是否移动端: false`** —— 这台不是手机。V8 存在的唯一理由，是回答
   「手机端到底该用哪种形态」（`docs/06-开发路线图与里程碑.md:65`）。
   **手机档的 V8 仍然是空的**，这一条不能拿桌面数据顶替。
2. **两个数字都是「到探针上限就停」，不是设备边界。**
   第一段 3072 MB 是当时写死的上限（`stressMemory(3072, ...)`），第二段 2048 MB 是
   `min(2048, 3072 × 0.95)`。两段都没摸到墙，所以 3072 与 2048 都是**下界**，
   真实值更大 —— 而报告把它们写成了确定值。这是探针的缺陷，不是设备的结论。

## 三、探针自身的两个缺陷（本轮已修）

### 缺陷 1：撞上限时把下界当成了精确值

- 现象：`第一段 空设备上限 3072 MB（首次失败 未失败）` —— 「未失败」和「上限 3072」摆在一起，
  本身就自相矛盾；`第二段 余量 2048 MB（到 2048 MB 上限主动停）` 同理。
- 后果：整份报告读起来像量到了边界，实际上什么都没量到。
- 修法（`src/probe/probes.ts` / `src/probe/ProbeApp.tsx`）：
  - 上限从写死的 3072 提到 `MEMORY_CEILING_MB = 5120`，让桌面有机会真的撞墙；
  - 第二段的上限不再乘 0.95，直接取**第一段已经证实拿得到的量**；
  - 到上限停住时，结论与明细一律写成 **`≥ X MB`**，并附一句
    「只量到下界，真实余量更大」。

### 缺陷 2：`堆占用` 是一个不可能的数

- 现象：`3185.27 → 3185.27 MB（内核上限 1077.65 MB）` —— used 比 limit 还大，
  而且加载两个模型前后**一个字节都没变**。
- 根因：`performance.memory` 量的是 **V8 的 JS 堆**。模型权重与探针自己分配的
  `Float32Array` 都是**堆外后备存储**，两边都不计入。所以这个数字对
  「边听边译要多少内存」**没有参考价值**。
- 修法：`MemoryResidentResult` 新增 `heapReadingSane`（`before <= limit && loaded <= limit`），
  报告里在不可信时直接写「**读数不可信** …… 这个数字对『边听边译』没有参考价值」，
  不再让一个假数字混进结论。

## 四、对架构的影响

**结论：三次都写 `是否移动端: false`；三份都只贴了 V8 段、没有「运行环境」段。所以「这台到底是不是手机」至今没有答案。**
第三次与第二次的堆占用读数不同（3585.82 对 3185.27），说明换了机器或换了会话；但两次的 `JS 堆上限 1077.65 MB` 逐位相同，属同一类 Chromium 内核。

两条互相矛盾的线索：

- 支持「是手机」：`1077.65 MB` 这个堆上限更像 Android 侧 Chromium 的取值（桌面 Chrome 通常是 2~4 GB）；5 GB 的 `Float32Array` 能被分配完，说明系统有大量可压缩/可换出的内存，手机 zram 正符合这个特征。
- 支持「不是手机」：探针当时的判定是 `/Android|iPhone|iPad|iPod|Mobile/i.test(navigator.userAgent)`，华为 / 荣耀 / 小米 / iPhone 的 UA 里都带 `Mobile`，真机不该漏。能同时解释两者的情形只有一种 —— **UA 被伪装成桌面**（浏览器开了「桌面版网站」，或 HarmonyOS NEXT 的 ArkWeb 报的是 `Mozilla/5.0 (Phone; OpenHarmony 5.0) …` 这类不含 Android / Mobile 的 UA）。

### 为此做的修复（本轮）

1. `src/lib/device.ts`：判定逻辑抽成 `mobileEvidence()`，**返回结论 + 逐条依据**（`signals`）。正则补 `HarmonyOS|OpenHarmony|ArkWeb`；保留 iPad 触点兜底；新增「触点数 > 2 且屏幕短边 ≤ 900」兜底。`isLikelyMobile()` 改成它的薄封装。
2. `src/probe/ProbeApp.tsx`：V8 段的 `是否移动端` 不再是一个裸布尔值，改成「是/否 —— 依据：…」，并新增两行「设备原始信息（自己核对）」：完整 UA + 触点数 + `uaData.mobile` + 屏幕 + 逻辑核心 + `deviceMemory`。P0 段也新增「是否移动端（含依据）」一行。
3. `src/probe/probes.ts`：`toMarkdownReport()` 现在**每一份报告都自带「设备指纹」段** —— 根因是每个 section 都有自己的复制按钮，用户只复制了跑过的那一段。与其反复要求「记得把运行环境也复制上」，不如让每一段自己带上指纹。

**下一次复测时，报告开头就会直接写着 UA 和判定依据，不再需要猜。**

## 六、设备身份已确认：第三份报告跑在**小米平板**上（用户 2026/10/7 确认）

用户在看到上面这张表之后明确答复（`m04510`，逐字）：

> 这个是小米的平板跑出来的

**这一句话把 R1 从「未知」变成「平板侧证否」。** 于是：

| 问题 | 结论 |
|---|---|
| 那台设备是移动端吗 | **是**，Android 平板 |
| `是否移动端: false` 说明什么 | **说明探针当时的判定漏了它**，不说明它是电脑。小米平板浏览器在「桌面版网站」模式下会报桌面 UA —— 这正是上面推断的那个情形，也说明 `device.ts` 里补 `OpenHarmony / ArkWeb / 触点 + 屏幕短边` 三条兜底是必要的 |
| `1077.65 MB` 的 JS 堆上限 | 与 Android 侧 Chromium 相符（桌面 Chrome 通常 2~4 GB） |
| 两模型同时驻留后 ≥ 5120 MB | **在这台平板上成立**，而且是撞在探针自己抬到 5120 MB 的上限上 —— 真实余量**比 5120 MB 更多**，不是「刚好 5 GB」 |
| 「边听边译」能不能做 | **在这台平板上可以**。R1（`docs/07`）针对平板的退路不必启用 |

**仍然存在的空白**：这是一台**平板**，不是手机。平板的内存（通常 8 GB 上下）普遍大于手机，所以这份报告**不能顶替手机档**。R1 里「真手机够不够」这一问仍然是空的 —— 而它才是决定「用户最可能拿在手上的那台设备能不能用」的问题。补这一档只需要在手机上再跑一次 V8，报告现在会自带 UA 与判定依据，不会再出现「不知道这是什么机器」的情况。
