# 01 · 需求与目标

## 1.1 原始需求（来自需求方原话，消息 m00001）

> 「我现在想做一个同声传译的一个项目就是把英语转化为中文，并且在。整个转化结束之后，帮我总结这所有这段话的要点，请现在帮我在github上面找到一个类似的项目，并且。学习这个项目，分析它的优点和缺点,我需要你。把这个项目做成一个网站，方便我传给朋友。让他使用。且这个项目使用时是免费，不需要花费任何费用,请你先帮我把这个项目的整个框架构建出来。，但是先不要开始做这个项目。」

## 1.2 需求拆解

### A. 功能性需求

| 编号 | 需求 | 优先级 | 说明 |
|---|---|---|---|
| F1 | 英文语音 → 中文实时翻译 | P0 | 「同声传译」核心，边说边出中文 |
| F2 | 双语对照显示 | P0 | 同时保留英文原文与中文译文，便于核对 |
| F3 | 结束后生成整段内容的要点总结 | P0 | 需求方特别强调的差异化功能 |
| F4 | 总结为中文、结构化 | P0 | 主题 + 要点条目 + 关键数字/结论 |
| F5 | 做成网站 | P0 | 浏览器打开即用 |
| F6 | 方便分享给朋友使用 | P0 | 一个链接/二维码即可，对方无需安装注册 |
| F7 | 全程零费用 | P0 | 需求方 + 使用者双方都不产生任何费用 |
| F8 | 上传音频文件转写 | P1 | 不只是麦克风，录好的会议音频也能处理 |
| F9 | 导出记录 | P1 | Markdown / TXT / SRT 字幕 |
| F10 | 历史记录本地留存 | P2 | 存 IndexedDB，不上云 |
| F11 | 多说话人区分 | P2 | 「谁说了什么」，难度高，后置 |

### B. 非功能性需求

| 编号 | 需求 | 目标值 |
|---|---|---|
| N1 | 实时延迟 | 首字上屏 ≤ 1.5s；整句出译文 ≤ 2.5s |
| N2 | 可用性 | 朋友的任意设备打开都能跑起来，最差也有降级可用 |
| N3 | 隐私 | 默认音频与文本不出设备；不采集、不埋点 |
| N4 | 零成本 | 托管、推理、存储全部落在免费额度内 |
| N5 | 免安装 | 纯前端静态站，无需后端服务即可完成主流程 |
| N6 | 可维护 | 模块边界清晰，每个环节可独立替换引擎 |
| N7 | 移动端可用 | 手机浏览器打开也能用（关键约束，见 §1.4） |

### C. 明确**不做**的事（范围外）

- 不做账号体系、不做付费墙、不做用户数据云端存储
- 不做语音合成输出（TTS）朗读中文 —— 需求未提，避免范围膨胀
- 不做多人协作房间（otoji 那种 WebRTC 网状房间）—— 一期不做，列为远期
- 不做中日/中韩等多语言翻译 —— 聚焦英译中

## 1.3 关键约束（硬约束，设计必须服从）

| 约束 | 来源 | 对设计的影响 |
|---|---|---|
| **必须零费用** | 需求方明确要求 | 排除所有按量计费 API（OpenAI / Deepgram / Azure 等）；只能走浏览器本地推理或免费额度 |
| **必须方便分享给朋友** | 需求方明确要求 | 不能是「先装 Python 再跑脚本」；必须是静态站 + 一个链接 |
| **朋友的设备不可控** | 推论 | 可能是手机、可能用 Safari、可能磁盘空间不足 → 必须有降级链路 |
| **Chrome 内置 Translator API 不支持移动端** | 官方文档实测限制（详见 03 文档） | 手机端必须另配翻译引擎 |
| **Chrome 内置 Translator API 要求 ≥22GB 可用磁盘 + 16GB 内存** | 官方文档实测限制 | 大量普通设备拿不到这个能力，降级链路是刚需而非可选项 |

## 1.4 关键发现：移动端是生死线

调研后确认了一个对产品形态有决定性影响的事实：

> Chrome 的内置 AI 翻译能力（`Translator` API）**只在桌面端 Chrome 138+ / Edge 148+ 可用，明确不支持 Android、iOS、Firefox、Safari**。

而「发给朋友用」的场景里，朋友**大概率是用手机打开的**。因此：

- **不能**把产品设计成「依赖内置 AI API」的桌面专用工具；
- **必须**把「手机能跑」当作一等公民，设计一条独立可用的降级链路。

这条约束直接决定了 [03 文档](03-技术选型与可行性验证.md) 中「渐进增强四层引擎」的架构。

## 1.5 验收标准（Definition of Done）

一期（M5）上线时，需同时满足：

1. 一部**桌面 Chrome** 和一部**手机（Android Chrome 或 iOS Safari）**分别打开同一个链接，都能完成一次「说英文 → 看中文 → 拿到纪要」的完整流程。
2. 全过程未产生任何费用，未配置任何付费密钥。
3. 断网状态下，桌面端（模型已缓存）仍能完成识别 + 翻译 + 摘要。
4. 朋友的设备上，浏览器控制台无未捕获异常；任一引擎不可用时界面给出明确提示并自动降级，不白屏。
5. 分享方式为：一个 URL + 一个二维码。

## 1.6 待确认问题（需要需求方拍板）

| 序号 | 问题 | 选项 | 默认建议 |
|---|---|---|---|
| Q1 | 主要使用场景是「一个人的讲话/会议」还是「双向对话」？ | 单向长讲 / 双向对话 | 一期按**单向长讲**设计，双向对话作为 P2 |
| Q2 | 使用者主要在桌面还是手机？ | 桌面为主 / 手机为主 | 两者都保，桌面优先体验 |
| Q3 | 是否需要「边听边出中文语音朗读」？ | 需要 / 不需要 | **不需要**（不在原需求内） |
| Q4 | 是否可以接受「首次打开需下载 200–400MB 模型」？ | 接受 / 不接受 | **接受**，页面明确提示进度，下载后永久缓存、后续离线可用 |
| Q5 | 是否接受「桌面用浏览器内置翻译（更快更自然）+ 手机用本地小模型（稍慢）」的体验差异？ | 接受 / 不接受 | **接受**，这是一期唯一能同时满足免费与移动可用的方案 |
| Q6 | 项目/网站叫什么名字？ | 自定 | 暂用 **SimulNote（同传笔记）** |
| Q7 | 是否需要「多人一起看同一场同传」的房间功能？ | 需要 / 不需要 | 一期**不需要**（会引入服务器成本，破坏零费用约束） |

## 1.7 成功指标（上线后观察）

- 朋友首次打开 → 成功产出纪要的完成率 ≥ 70%
- 手机端完成率 ≥ 40%（若无此项说明降级链路仍太重）
- 单次 10 分钟讲话的端到端延迟中位数 ≤ 2s
